## 2. Core

### 2-0. Core가 뭔가

`Assets/_Project/Scripts/Core/` — **다른 레이어가 공통으로 기대는 바닥**이다. 약 2,800줄.

```
Core/
├── GameInput.cs                    입력 (유일한 입력 창구)
├── IHarvestable / IDamageable / IInteractable    "대상" 인터페이스 3종
├── HarvestRewardService.cs         광물 보상 처리 순서
├── CombatRewardService.cs          몬스터 처치 보상
├── Items/       아이템 정의(SO), 스택, 컨테이너, 소모품 효과, 장비·버프 정의
├── Crafting/    CraftRecipe (SO)
├── Grid/        MapGrid, GridPlacement, GridOccupancy, MapFolder, MapPalette
├── Pooling/     PoolManager, GameObjectPool, PooledInstance, IPooled
├── Save/        ISaveable 3종 인터페이스, SaveService, SaveCatalog
└── Regions/     구역 정의·조건·맵·개방·통과 판정·진입 추적
```

**Core에 들어가는 기준**: 특정 게임 오브젝트(플레이어, 몬스터, 상점)를 몰라도 성립하는 것.
규칙(컨테이너, 그리드, 저장), 계약(인터페이스), 데이터 정의(SO)가 여기 있다.
`Player`·`World`·`Economy`는 Core를 쓰고, Core는 그쪽을 거의 모른다.

> 예외가 둘 있다. 보상 서비스는 `MineralNode`·`Monster`·`Inventory`·`PlayerLevel`을 직접 안다
> (처리 순서를 한 곳에 모으는 게 목적이라 일부러 그렇게 뒀다).
> 구역 조건(`RegionContext`)도 `PlayerLevel`·`Inventory`·`GoldWallet`·`ProgressFlags`를 들고 있다.

### 2-1. 입력 — `GameInput`

**한 줄**: 키 입력은 여기서만 읽고, 나머지는 이벤트를 받거나 값을 폴링한다.

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| InputAction을 **에셋이 아니라 코드로** 생성 | 템플릿 에셋은 Interact가 E인데 사양은 F. 에셋을 고치는 대신 사양을 코드에 그대로 박아 어긋날 일을 없앴다 | 키 리바인딩 UI를 붙이려면 다시 에셋/저장 구조가 필요하다 |
| **`GameplayBlocked` 플래그 하나**로 게임 입력을 끊음 | 휠만 막아서는 부족했다. 상점에서 버튼을 누르면 칼이 나가고 WASD로 걸어다녔다 | ESC·I·M·탭 이동은 **절대 막지 않는다**. 창을 닫을 길까지 끊으면 못 빠져나온다 |
| 그 플래그를 **UiRouter가 밀어 넣음** (입력이 UI를 참조하지 않음) | 입력이 UI를 알면 입력만 떼어 시험할 수 없다 | `UiRouter`가 꺼지면 `false`로 돌려놔야 한다 (`OnDisable`에서 처리 중) |
| 좌클릭 **누른 시간과 뗀 순간을 여기서만** 잼 (`AttackHoldTime`, `AttackReleased`) | 컴포넌트마다 직접 재면 `Update` 실행 순서에 따라 값이 어긋난다 | 창이 열리며 `AttackHeld`가 false가 되면 그 순간 `AttackReleased`가 나간다 |
| 핫바 숫자키는 **InputAction 없이 키 배열 직접 읽기** | 액션 9개 선언 + 어느 키였는지 역추적보다 짧고 분명 | 패드 지원 시 따로 붙여야 함 |
| **E = 설치이자 다음 탭** | 창이 있으면 설치가 막히고, 창이 없으면 탭 이동을 받는 쪽이 무시 → 실제로 안 겹침 | 둘 중 하나의 규칙이 바뀌면 충돌한다 |
| `PointerPosition`의 null 처리를 **여기서** | 마우스 없는 환경에서 `Pointer.current`가 null. 호출부마다 막게 두면 반드시 하나 빠진다 | |

### 2-2. 상호작용 인터페이스 3종

**한 줄**: 대상 판별은 태그·레이어 문자열이 아니라 **컴포넌트(인터페이스) 조회**로 한다.

| 인터페이스 | 구현 | 쓰는 쪽 |
|---|---|---|
| `IHarvestable` | `MineralNode` | `PlayerAttacker` 채집 |
| `IDamageable` | `Monster`, `PlayerHealth` | `PlayerAttacker`, 몬스터 공격, 투사체 |
| `IInteractable` | `ItemDrop`, 스테이션 4종, `RegionBarrier` | `PlayerInteractor` (F) |

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| `OverlapSphere` → `GetComponentInParent<인터페이스>()` | 레이어 설정이 깨져도 판정이 안 죽는다 (과거에 TagManager 캐시가 깨져 `LayerMask`가 0이 된 적 있음). 대상이 늘어도 판정 코드가 안 는다 | 콜라이더가 많은 곳에선 `GetComponentInParent` 비용이 든다. 지금 규모에선 무시 가능 |
| `IHarvestable`과 `IDamageable`을 **일부러 분리** | 좌클릭 판정 경로는 공유하지만, 보상 처리가 섞이면 안 된다 | |
| `DamageKind`는 **enum 두 값** (`Normal`, `Unblockable`)뿐 | 지금 필요한 구분은 "방패에 막히냐"뿐. 특수 공격 스펙이 아직 없다 | 공격 성질이 늘면 여기 값을 늘린다 |
| `TakeDamage(amount, source, kind = Normal)` — **source를 넘김** | 방패 각도·넉백 방향·반격(어그로) 판정이 "누가 때렸나"를 알아야 한다 | 투사체는 **투사체 자신**을 source로 넘긴다 → 막혀도 쏜 몬스터는 경직 안 됨 |

### 2-3. 보상 서비스

**한 줄**: 대상은 "나 캐졌다/죽었다" 이벤트만 쏘고, **보상 순서는 서비스 한 곳이 소유**한다.

```
MineralNode ⇒ Harvested ─► HarvestRewardService ─► DropService.Spawn → PlayerLevel.AddExp
Monster     ⇒ Died      ─► CombatRewardService  ─► (토글이 켜져 있으면) PlayerLevel.AddExp
```

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 처리 순서를 **노드가 아니라 서비스**에 둠 | 사양에 "광물 → 경험치 → 레벨 판정 → UI" 고정 순서가 있었다. 노드 안에 넣으면 광물 종류마다 순서가 복제된다 | |
| UI 갱신은 서비스가 안 함 | 각 데이터의 `Changed` 이벤트가 하므로 **호출 순서가 곧 갱신 순서** | |
| 캔 자원은 **인벤으로 직행하지 않고 바닥에 드랍** | 확정 사양. 가방이 꽉 차도 캘 수 있어야 한다 | `DropService`가 없는 씬에선 예전처럼 인벤에 바로 넣는다 (기능이 죽지 않게) |
| 시작할 때 `FindObjectsByType`으로 **한 번만** 수집 | 맵이 고정 배치고, 노드·몬스터는 죽어도 파괴되지 않고 렌더러만 꺼서 참조가 유효 | **실행 중 생긴 대상은 모른다.** 설치한 광물 블럭은 `Track(node)`로 따로 넣는다. `MonsterSpawner`로 만든 몬스터는 아직 안 붙는다 |
| 몬스터 처치 경험치는 **수치를 0으로 지우지 않고 토글(`_grantExpOnKill`)로 막음** | 회의 결정(2026-09-28)으로 끔. 수치를 지우면 되살릴 때 균형값을 다시 잡아야 하고, 밸런스 표에서 실수로 켜질 수 있다 | |
| 설치 블럭 경험치 0은 **노드가 판단**(`GrantsExp`) | 놓고 캐기 무한 파밍 차단. 노드 자신이 설치물인지 안다 | |

### 2-4. 아이템 데이터

**한 줄**: 정의는 ScriptableObject, 수량은 `ItemStack`, 칸 규칙은 `ItemContainer` 한 곳.

```
ItemDefinition (SO)            가방에 들어가는 모든 것
 ├─ MineralDefinition          + 체력·산출량·경험치·재생성
 └─ ConsumableDefinition       + List<ConsumableEffect> (추상 SO)
EquipmentDefinition (SO)       ※ ItemDefinition 아님 — 가방에 안 들어감
BuffDefinition (SO)            지속 시간 + % 수치
CraftRecipe (SO)               재료 → 시간 → 장비 or 아이템
ItemStack (class)              정의 + 수량
ItemContainer (순수 class)     List<ItemStack> + 칸 수 + 규칙
```

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| **정의 = SO, 진행 상태 = 컴포넌트** | SO에 진행 상태를 넣으면 에디터에서 바뀐 값이 에셋에 저장돼 다음 플레이에 남는다 | SO 필드는 런타임에 절대 쓰지 않는다 |
| `ItemStack`은 **class** (struct 아님) | `List<ItemStack>` 안에서 수량만 바꾸는데, struct면 복사본이 수정돼 원본이 안 바뀐다 | |
| `ItemContainer`는 **MonoBehaviour가 아닌 순수 클래스** | 같은 규칙을 가방과 보관함이 함께 쓴다. 규칙이 두 군데 있으면 한쪽만 고치는 사고가 난다 (넘침 처리 때 실제로 겪음) | 컨테이너 자체는 들고 있는 쪽을 모른다. `Changed`를 자기 이벤트로 다시 쏘는 건 `Inventory`/`StorageBox` 몫 |
| `Add`/`Remove`는 **실제로 처리한 수량을 반환** | 넘침 처리를 호출자가 한 줄로 얹을 수 있게 | ⚠️ **반환값을 버리면 넘친 만큼 조용히 증발**한다 |
| `SpaceFor(def)`를 따로 둠 | 사는 쪽은 돈을 **내기 전에** 들어갈지 알아야 한다. `Add`를 불러보고 알 수는 없다 | |
| `Add`는 **기존 스택부터** 채움 | 새 칸부터 만들면 칸이 불필요하게 쪼개진다 | |
| `Remove`는 **뒤에서부터** | 중간 칸이 비어 지워질 때 인덱스가 밀리지 않게 | 보관함에서 "누른 칸"이 아니라 같은 종류의 마지막 칸부터 빠진다 |
| 리스트에 **빈칸이 없다** (빈 스택은 즉시 제거) | 단순함. 슬롯 번호 = 리스트 인덱스 | 칸을 비우면 뒤 칸이 앞으로 당겨진다. 칸 위치를 고정하는 UI(드래그 정렬)는 지금 구조로 불가 |
| `MoveTo`는 **받는 쪽에 먼저 넣고 들어간 만큼만 뺌** | 반대로 하면 받는 쪽이 꽉 찼을 때 뺀 게 갈 곳 없이 사라진다 | |
| 칸 **줄이기 없음** (`ExpandSlots`만) | 넘치는 칸 처리 규칙이 없다 | |
| 저장 모양도 **컨테이너에** 둠 | 가방과 보관함이 같은 형식을 쓰게. 한쪽만 바뀌어 다른 세이브가 조용히 깨지는 일 방지 | |
| 불러올 때 **사라진 에셋의 칸만 버림** | 아이템 하나 지웠다고 세이브 전체가 죽으면 개발이 막힌다 | |
| 소모품을 **상속으로 분리** (`ItemDefinition`에 효과를 달지 않음) | 광물까지 "쓸 수 있는 것"이 되면 E를 눌렀을 때 아이템마다 따져야 한다. 타입으로 가르면 "소모품이냐"만 물으면 된다 | |
| 소모품은 **효과 중 하나라도 쓸 이유가 있을 때만** 닳음 | 체력이 가득인데 회복약이 사라지면 안 된다 | ⚠️ 새 효과를 만들면 `CanUse`("언제 써도 소용없나")를 반드시 정할 것. 기본값이 "언제나 사용 가능"이라 안 정하면 아이템만 닳는다 |
| 장비는 **종류별 클래스 없이 한 타입** + `EquipmentSlot` enum | 도구·무기·방어구의 차이는 "어느 자리"와 "어느 수치"뿐이고 둘 다 값이다. 나누면 장착·구매·저장이 세 갈래가 된다 | 장비 전용 특수 능력이 생기면 스킬처럼 효과를 추상 SO로 뺀다 |
| 장비 교체 규칙은 **`Tier` 숫자 비교 하나** | 중복 불가·건너뛰기 허용·하향 금지가 전부 이걸로 끝난다 | |
| 피해 감소는 **정수가 아니라 %** | 기획 문구가 "10% 감소". 정수로 두면 적이 강해질수록 방어구가 무의미해진다 | |
| 버프 수치를 **장비와 같은 종류**로 맞춤, 전부 **%** | 합산하는 자리가 늘면 안 된다. 기획이 "증가율을 다 더한 뒤 한 번 계산"으로 못박음 | 출처마다 따로 곱하면 두 개만 겹쳐도 거의 무적이 된다 → **더하고 마지막에 한 번 곱한다** |
| 이름이 비면 **에셋 파일명**을 표시명으로 | 디자이너가 한 군데만 고쳐도 되게 | 파일명은 **영문 강제** (한글 리터럴 깨짐 사고, `ARCHITECTURE.md` 6절) |
| 겉모습(아이콘·색·드랍/설치 프리팹)을 **정의가 들고 있음** | 아트 교체가 에셋 수정으로 끝난다 | |
| 구역당 설치 제한을 **수치 필드**(`_maxPerRegion`)로 | 보관함 "구역당 1개"에서 나왔지만, 같은 제약이 다른 설치물에 오면 필드 하나로 끝 | |
| 제작대 구분은 **문자열 카테고리** | 보스 전용 제작대도 "카테고리가 다른 제작대"일 뿐 | 오타에 약하다 |

### 2-5. 그리드

**한 줄**: 그리드는 **배치 전용**이다. 플레이어·몬스터 이동은 그리드와 무관한 자유 물리 이동.

| 구성 | 역할 |
|---|---|
| `MapGrid` | 칸 ↔ 월드 좌표 변환. 칸 (0,0)의 **중심**이 이 오브젝트 위치 |
| `GridPlacement` | 배치물이 드는 칸·크기·회전. 인스펙터에서 칸을 고치면 바로 스냅 |
| `GridOccupancy` (static) | 어느 칸이 차 있는지 아는 유일한 창구 |
| `MapFolder` | 배치 도구가 "넣을 그룹"으로 인정하는 표시 |
| `MapPalette` (SO) | 배치 팔레트 항목. **런타임 코드는 안 읽음** |

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 1칸 = 1m, XZ 평면 정수 좌표 | 단순함 | |
| `WorldToCell`은 **반올림** | 칸 중심 기준 좌표계라 반올림이 곧 "가장 가까운 칸" | |
| 여러 칸짜리는 **최소 코너 칸이 기준점** | 크기가 짝수면 중심이 칸 경계에 걸려서 | |
| 회전하면 **가로세로를 뒤집은 칸**을 점유 (`RotatedSize`), 스케일은 회전 전 크기로 | 회전은 `transform.rotation`이 이미 처리. 스케일에 `RotatedSize`를 쓰면 회전이 두 번 적용된다 | |
| `[ExecuteAlways]` | 에디터에서 칸을 고치면 바로 스냅되어야 디자이너가 쓴다 | 에디터에서 쌓인 static 데이터가 플레이로 넘어온다 → 아래 리셋 |
| 점유를 **물리(OverlapBox)가 아니라 사전**으로 | 캐고 재생성을 기다리는 광물은 콜라이더가 꺼져 있다. 물리로 물으면 빈 칸으로 보여 블럭이 놓이고, 광물이 되살아날 때 서로 뚫는다. 점유는 "지금 보이는 모양"이 아니라 그리드가 기억할 사실 | 살아 움직이는 것(플레이어·몬스터)은 여기 없다. 블럭 설치 시 그쪽은 물리로 따로 확인 |
| `GridPlacement`가 **켜지고 꺼질 때 스스로 등록/해제** | 누가 대신 관리하면 반드시 빠뜨린다 | |
| 해제할 때 **주인 확인** 후 지움 | 디자이너가 두 구조물을 겹쳐 놨을 수 있다. 남의 칸까지 지우면 안 됨 | 겹치면 나중에 등록한 쪽이 칸을 가진다 |
| 조회 중 **파괴된 주인은 그 자리에서 정리** | 파괴 순서를 믿지 않음 | |
| `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]`으로 **플레이 진입 시 static 비우기** | 도메인 리로드를 꺼도 에디터 항목이 섞이지 않게 | static 레지스트리를 새로 만들면 **반드시 같이 붙일 것** |
| `MapGrid.Active`는 **지연 탐색** | 도메인 리로드로 static이 날아가도 찾아서 복구 | 씬에 `MapGrid`는 하나라는 전제 |
| 배치 결과는 **씬 오브젝트 + 칸 좌표** | 런타임 맵 생성 금지 원칙 | 예외는 플레이어가 설치하는 블럭(`PlacedBlocks`)뿐 |

### 2-6. 오브젝트 풀

**한 줄**: 자주 생겼다 사라지는 것만 풀링한다. **풀은 성능 장치지 필수 의존이 아니다.**

```
PoolManager.Spawn(prefab, ...)      static. 매니저 없으면 그냥 Instantiate
  └ GameObjectPool.Get             프리팹당 풀 하나. 유휴 꺼내기 or 생성 → 켜기 → IPooled.OnSpawnedFromPool
PoolManager.Despawn(go)             꼬리표 없으면 Destroy
  └ PooledInstance.Release → GameObjectPool.Release
                                    이중 반납 거부 → IPooled.OnReturnedToPool → 끄기 → 유휴 상한 넘으면 Destroy
```

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 대상: **드랍, 데미지 숫자, 몬스터 체력바, 투사체** | 자주 생기고 사라지는 것 | 광물·몬스터는 **풀 대상이 아니다**. 파괴하지 않고 렌더러만 끈다 |
| 매니저가 **없어도 Spawn/Despawn 동작** | 테스트 씬 등에서 풀이 없다고 기능이 죽으면 안 된다 | |
| 호출자는 **풀 객체를 모름** (static `Spawn`/`Despawn`) | 아무 데서나 반납할 수 있게 | `PooledInstance` 꼬리표가 "어느 풀 소속"을 들고 있다 |
| **이중 반납 방지** (`IsInUse`) | 같은 오브젝트를 두 번 반납하면 유휴 스택에 두 번 들어가 두 곳에서 동시에 쓰인다 | |
| 초기화는 `Awake`/`OnDestroy`가 아니라 **`IPooled` 두 지점** | 풀은 오브젝트를 파괴하지 않고 재사용 | 풀링되는 컴포넌트는 이전 사용 상태(타이머, 구독)를 여기서 되돌려야 한다 |
| `OnSpawnedFromPool`은 **SetActive 이후** | 꺼진 상태에서는 코루틴을 못 돌린다 | |
| **유휴 상한** (`MaxIdle`) | 한 번 크게 튄 사용량이 메모리에 눌러앉지 않도록 | |
| 풀마다 **전용 부모** `Pool_<이름>` | 하이어라키에서 무엇이 얼마나 재워져 있는지 바로 보이게 | |
| 사전 키 = **프리팹 참조** | 이름 충돌 없음 | |
| `Prewarm` | 첫 사용 때 생성 비용이 몰리는 것 방지 | |

### 2-7. 저장

**한 줄**: 저장 서비스는 **내용을 하나도 모른다.** 각 시스템이 자기 몫을 JSON으로 접어 내놓고 돌려받는다.

```
ISaveable        SaveKey · Capture() → string · Restore(string)
ISaveMilestone   event Milestone(사유)  — "되돌리기 어려운 일이 났다" (선택)
ISaveSummary     SummaryOrder · Describe() — 슬롯 목록 한 줄 (선택)

SaveService      씬의 ISaveable 수집 → 키 순서로 Capture/Restore, 파일 쓰기, 자동 저장
SaveCatalog (SO) 에셋 이름 → 에셋 명부
```

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| **시스템이 자기 데이터를 스스로 꾸림** (`ISaveable`) | 세이브가 각 시스템 속을 들여다보면 제작·방어구·보관함이 들어올 때마다 세이브 쪽을 연다 | |
| 묶음을 **문자열(JSON)**로 주고받음 | 시스템마다 저장 모양이 다르다. 공통 타입을 만들면 새 시스템마다 그 타입을 고쳐야 한다 | 이중 JSON(문서 안에 JSON 문자열)이라 파일이 조금 읽기 불편 |
| `SaveKey`는 **한 번 정하면 안 바꿈** | 바꾸면 옛 저장이 그 칸을 잃는다 | |
| **같은 상태면 같은 문자열** (`Capture` 결정성) | 자동 저장이 직전 문자열과 비교해 "저장할 게 생겼나"를 판단 | ⚠️ 목록은 **정렬**해서 담을 것 (`HashSet` 순회 순서는 실행마다 다름). 시간은 **정수 초로 버림** |
| 에셋은 **이름**으로 저장 (`"Mineral_Iron"`) | 사람이 열어 읽고 손으로 고칠 수 있어야 문제 원인을 찾는다 | ⚠️ 에셋 **이름을 바꾸면** 옛 저장에서 그 항목이 사라진다. 이름 중복도 금지 (검사기가 잡음) |
| 이름 → 에셋은 **`SaveCatalog` 에셋** (Resources 아님) | Resources는 경로 규칙이 안 보이고 빌드에 뭐가 들어갔는지 확인할 수 없다. 명부는 눈으로 보이고 검사기가 짚을 수 있다 | 새 SO 종류를 저장하면 명부 수집 대상에 넣을 것 (에디터 버튼으로 자동 수집) |
| 저장 시점 = **주기 + 큰 사건(`ISaveMilestone`)** | 채집·인벤 숫자 같은 잔 변화로 저장하면 캘 때마다 디스크를 때린다. 잔 변화는 다음 주기 저장에 묻어감 | 강제 종료 시 몇 분 날아가는 건 감수 |
| 무엇이 "큰 사건"인지 **시스템이 직접 선언** | 기획 판단이라 코드가 짐작하면 안 된다 | |
| 사건이 몰리면 **최소 간격 + 보류(`_pending`)** | 연달아 쓰지 않도록 | |
| **임시 파일에 다 쓰고 바꿔치기** (`.tmp` → 이동) | 쓰는 도중 꺼지면 반쪽 파일이 남는다 | 삭제와 이동 사이에 꺼지면 `.tmp`만 남을 수 있다 |
| 불러오는 동안 **`_restoring`** | 복원 도중의 어중간한 상태가 저장되지 않게 | |
| 저장에 **없는 키는 건드리지 않음** | 그 시스템이 나중에 생긴 경우라 시작값 그대로가 맞다 | |
| 버전이 다르면 **변환 없이 거부** | 형식이 자주 바뀌는 동안 어설프게 변환하면 틀린 상태로 조용히 굴러간다 | **출시 전에 변환을 붙여야 한다** |
| `Restore`는 **키 사전순** | 결정적이고 단순함 | 시스템 간 복원 순서 의존이 생기면 키 이름으로 순서를 맞추게 된다. 지금은 `level` 복원 반응을 뒤의 `skills`·`regions`가 덮어써서 괜찮다 |
| 수집 시 **비활성 오브젝트 포함** | 창처럼 꺼둔 채 상태를 들고 있는 것이 있다 | |
| 슬롯 = `persistentDataPath/save_{n}.json` | | 시작 시 자동 불러오기는 없다 |

### 2-8. 구역

**한 줄**: 구역 정의·조건은 SO, **개방 상태는 `RegionAccess` 한 곳**, 칸 → 구역은 정적 사전.

| 구성 | 역할 |
|---|---|
| `RegionDefinition` (SO) | 이름, 색, 조건 목록, 영구 개방 여부, 벽 모양 |
| `RegionRequirement` (추상 SO) | `IsMet` / `Describe` / `Consume` / `HasCost` — 하위: 레벨·골드·아이템·플래그 |
| `RegionVolume` | 씬의 사각 범위 → `RegionMap`에 등록 |
| `RegionMap` (static) | 칸 → 구역 |
| `RegionAccess` | "들어갈 수 있나"의 **단일 창구** + 개방 상태 + 저장 |
| `RegionGate` (static) | "저기 있는 걸 건드려도 되나" |
| `RegionTracker` | 플레이어 현재 구역, 잠긴 구역이면 되돌려 보냄 |

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 새 구역 = **에셋 하나 + 씬에 범위**, 코드 수정 없음 | 구역 간 차이는 대부분 **배치**(어떤 광물·몹을 놨나)로 표현된다 | |
| 조건 = **추상 SO 목록** | 기획이 어떤 조건을 들고 올지 모름. 종류가 늘어도 상속 에셋 하나 추가로 끝, 구역·벽·UI는 안 건드림 | |
| 조건이 **자기 설명 문구**를 만듦 (`Describe`) | 조건이 늘 때 UI 쪽에 `if`가 쌓이지 않게 | |
| 조건에 **`RegionContext` 묶음**을 넘김 | 조건이 `Inventory`·`GoldWallet`을 직접 찾아다니면 테스트·교체가 어렵다 | |
| 개방 상태는 **SO가 아니라 `RegionAccess`** | SO에 담으면 에디터에서 연 상태가 저장돼 다음 플레이에 남는다 | |
| **전부 확인한 뒤에 치름** (`TryUnlock`) | 하나씩 확인하며 치르면 중간에 막혔을 때 앞의 것만 빠져나간다 | |
| **대가 있는 구역은 저절로 안 열림** (`HasCost`) | 골드가 모였다고 플레이어 의사 없이 땅을 사버리면 안 된다 | |
| 재평가는 **레벨업·플래그 때만** (`ReevaluateAll`) | 매 프레임 조건 수 × 구역 수를 돌리지 않으려고 | 새 조건 종류가 다른 이벤트(골드·아이템)에 반응해야 하면 구독을 추가해야 한다 |
| `ReevaluateAll`은 **`Start`에서** | 볼륨들이 `OnEnable`에서 등록을 마친 뒤라야 구역 목록이 찬다 | |
| `Context`를 **지연 생성** | `Awake`에서만 채우면 에디터 도구가 물었을 때 null → 실제로 터졌다 (문 안내 문구 미리보기) | |
| `RegionGate`는 **판정 불가면 통과 (fail-open)** | 막는 쪽이 더 위험하다. 구획을 안 그은 맵에서 아무것도 못 캐게 된다 | |
| `RegionGate`와 몬스터의 "같은 구역" 판정을 **합치지 않음** | 저쪽은 "같은 구역인가", 이쪽은 "그 구역이 열렸나". 묻는 게 다르다 | |
| 잠긴 구역 것은 **캐지도 F로 열지도 못함** (벽 제외) | 벽에 붙어 벽 너머 자원을 캐는 일이 실제로 나왔다 | |
| `RegionMap`은 **칸 사전** | 플레이어 위치 판정이 자주 불리는 자리라 조회를 한 번에 | `GridOccupancy`와 같은 정적 레지스트리 패턴 (리셋 포함) |
| 영구 개방을 **스위치**(`_permanentUnlock`)로 | 기획이 통행료 방식을 고르더라도 흡수하려고 | ⚠️ 꺼진 구역은 지금 코드에서 사실상 못 들어간다 (`LOGIC_MAP.md` 17절) |

### 2-9. Core에서 반복되는 패턴

Core를 읽다 보면 같은 모양이 계속 나온다. 새 코드를 쓸 때 이걸 따르면 나머지와 어울린다.

| 패턴 | 어디서 | 요점 |
|---|---|---|
| **정의 = SO / 상태 = 컴포넌트** | 아이템, 장비, 버프, 레시피, 구역, 몬스터, 스킬 | SO 필드는 런타임에 쓰지 않는다 |
| **종류가 늘 것 같으면 추상 SO 목록** | 구역 조건, 소모품 효과, 스킬 효과, 상점 효과, 몬스터 공격 | 새 종류 = 상속 클래스 하나 + 에셋. 쓰는 쪽은 안 고침 |
| **효과에 Context 묶음을 넘김** | `RegionContext`, `ConsumableContext`, `SkillContext`, `ShopContext` | 효과가 시스템을 직접 찾아다니지 않게 |
| **Context는 지연 생성** | `RegionAccess`, `SkillBoard`, `ConsumableUser`, `ShopStation` | 에디터에서 `Awake` 전에 불려도 안 터지게 |
| **정적 레지스트리 + 자기 등록 + 플레이 진입 리셋** | `GridOccupancy`, `RegionMap`, `RegionGate` | `OnEnable` 등록 / `OnDisable` 해제 / 주인 확인 후 해제 / `SubsystemRegistration` 리셋 |
| **반환값 = 실제로 처리한 양** | `ItemStack`, `ItemContainer`, `GoldWallet.TrySpend` | 넘침·부족 처리를 호출자가 한 줄로 |
| **먼저 받고, 들어간 만큼만 뺀다** | `ItemContainer.MoveTo` | 받는 쪽이 꽉 차도 사라지는 게 없다 |
| **전부 확인한 뒤 치른다** | `RegionAccess.TryUnlock`, `ShopStation.TryBuy` | 중간 실패 시 일부만 빠져나가지 않게 |
| **실패 사유를 문자열로 돌려줌** | `CanUse(out reason)`, `CanLearn`, `CanBuy`, `CanStart` | UI가 그대로 띄운다. 버튼 활성화도 같은 함수로 |
| **이벤트는 데이터가 쏘고 UI가 듣는다** | `Changed`, `Milestone`, `OpenRequested` | 데이터는 UI를 모른다 |
| **없어도 안 죽는다** | `PoolManager`, `DropService`, `RegionGate` | 보조 장치가 빠지면 단순한 대체 경로로 |
| **시작 시 한 번 수집** | 보상 서비스, `CombatFeedback`, 체력바 | 고정 배치 전제. ⚠️ 런타임 생성물은 따로 등록 |
| **인스펙터 연결 → 비었으면 `FindFirstObjectByType`** | 거의 모든 컴포넌트 | 팔레트로 찍은 프리팹은 씬 참조가 비어 온다 |
| **이름이 비면 에셋 파일명** | 모든 `DisplayName` | 파일명은 영문 |

### 3-1. 행동 판정자 — `PlayerActionState`

**한 줄**: "대시 중 방패 금지" 같은 규칙을 **한 파일에만** 둔다. 각 행동은 자기 상태만 공개하고, 허용 여부는 여기에 묻는다.

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 우선순위 규칙을 **중재자 한 곳**에 | 각자 판단하면 "방패 중 공격 금지", "대시 중 방어 금지"가 다섯 군데로 흩어져 서로 어긋난다 | 새 행동(점프 등)을 넣으면 여기 규칙부터 고친다 |
| 판정자는 **읽기만** 하고 아무것도 호출하지 않음 | 호출이 순환하지 않는다. 각 행동 → 판정자 → 각 행동의 상태, 한 방향 | 상태가 바뀐 **그 프레임**의 실행 순서에 따라 한 프레임 늦게 반영될 수 있다 |
| 이동 **소유권**(`MovementOwnedByOther`)과 **배율**(`MoveSpeedMultiplier`)을 분리 | 넉백은 위치를 직접 옮기므로 이동이 손을 떼야 한다. 대시·방패·차지는 소유권을 뺏지 않고 속도만 바꾼다 | |
| 배율은 **처음 걸리는 하나만** (대시 > 방패 > 차지) | 곱하면 "방패 들고 차지" 같은 조합이 예측하기 어려워진다 | |
| **조준 소유권**(`AimOwnedByOther`)도 여기서 | 스윙이 적 쪽으로 돌려놨는데 다음 프레임에 커서 조준이 8방향으로 덮어쓰면 보정이 한 프레임 만에 사라진다 | |
| 규칙 3개: `CanAttack` / `CanShield` / `CanDash` | 확정 스펙 (방패 중 공격·대시 불가, 대시 중 방어 불가, 넉백 중 전부 불가) | 주석의 "경직(stagger)"은 플레이어에 없다 |

### 3-2. 이동 · 조준 · 카메라

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 이동은 **`Rigidbody.MovePosition`** (`FixedUpdate`) | transform 직접 이동과 달리 콜라이더를 밀어내며 보간도 유지된다 | 넉백도 같은 방식이어야 서로 상쇄되지 않는다 (`ARCHITECTURE.md` 6절) |
| 대각 입력 **정규화** | 대각선이 √2배 빨라지지 않게 | |
| 물리 회전 **잠금** (`freezeRotation`) | 조준 회전을 직접 세팅하므로, 충돌로 캐릭터가 돌아가면 안 된다 | |
| 조준은 `Update`, 이동은 `FixedUpdate` | 조준은 화면 반응이라 매 프레임, 이동은 물리 | |
| 커서 → **플레이어 높이의 수평면**에 레이 | 탑다운이라 바닥 콜라이더 대신 평면에 투영 | |
| **8방향 스냅** (45°, 0이면 자유) | 판정이 부채꼴이라 조준이 연속이면 "맞을 각인데 안 맞는다"가 생긴다. 각을 이산화해 읽기 쉽게 | 자동 조준 때는 스냅을 끈다 (보정한 각이 도로 어긋나므로) |
| 커서가 발밑이면 **직전 방향 유지** | 길이 0 벡터로 회전하면 튄다 | |
| `transform.forward`가 **"정면"의 유일한 기준** | 공격·채집·방패가 전부 이걸 읽는다 | 조준을 바꾸면 세 판정이 함께 바뀐다 |
| **낙하 구제**: y < 한계면 `PlayerHealth.Respawn()` | 바닥 아래로 빠지면 스스로 못 돌아온다 | 체력도 가득 찬다(사망과 같은 경로) |
| 카메라는 **`LateUpdate`**, 지수 보간 `1 - exp(-k·dt)` | 플레이어 이동 뒤에 따라가야 한 프레임 밀리지 않는다. 지수 보간은 프레임레이트와 무관하게 같은 속도 | 각도 고정. 맵이 30m 넘게 벌어져 고정 프레임으론 한 화면에 안 들어와서 추적 |

### 3-3. 대시

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 대시 = **이속 부스트** (순간이동 아님) | 이동 소유권은 `PlayerMotor`가 계속 쥔다. 벽 통과·충돌 처리 문제가 안 생긴다 | 거리는 `속도 배율 × 지속 시간`으로 간접 결정 |

| **무적은 기본 꺼둠** (`_invulnerableTime = 0`) | 확정 스펙. 자리만 뚫어둠 | 켜면 `PlayerHealth`가 이미 읽고 있어서 그쪽 코드는 그대로 |

### 3-4. 좌클릭 — `PlayerAttacker`

**한 줄**: 좌클릭 하나로 채집과 전투를 겸한다. **누르는 첫 프레임에 모드를 정하고 뗄 때까지 고정.**

```
누름 ─ 정면에 광물? ─ 예 ─► 채집 모드: 간격마다 MineralNode.Harvest      (떼면 끝, 스윙 없음)
                    └ 아니오 ► 차지 모드: 게이지 참 → 떼면 스윙(완충이면 차지 스윙)
스윙: Windup → Active(매 프레임 판정) → Recovery → Idle
```

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 채집과 공격이 **같은 버튼, 같은 판정 경로** | 포레이저식 조작. 대상이 광물이냐 몬스터냐로만 갈린다 | 인터페이스는 분리 (보상이 섞이면 안 됨, [2-2](#2-2-상호작용-인터페이스-3종)) |
| 모드를 **누른 순간 잠금** | 캐는 도중 광물이 깨져도 갑자기 차지로 바뀌지 않게. 캐다가 원치 않는 차지가 걸리면 안 된다 | 정면 부채꼴에 광물이 있으면 누른 동안 내내 채집이라, 광물 옆의 몬스터에게는 스윙이 안 나간다 |
| **채집 중 떼면 스윙 안 나감** | | |
| 채집·공격이 **후딜을 공유** (`_shareActionCooldown`) | 따로 세면 캐다가 바로 베고 또 바로 캐서 두 박자가 겹쳐, 한쪽만 보고 잡은 밸런스가 무너졌다 (2차 프로토타입 피드백) | 스윙 직후 채집 간격만큼 못 캔다. 반대도 마찬가지 |
| 스윙 = **선딜 · 액티브 · 후딜 3구간**, 판정은 액티브에만 | 확정 스펙. 회피 여지를 남기면서 연타가 끊기지 않게 | |
| 액티브 동안 **매 프레임 판정** + `_hitThisSwing`으로 중복 차단 | 한 프레임만 보면 그 순간 범위 밖이던 적이 빠진다 | |
| 기본 평타는 **한 스윙에 한 명** | 액티브가 여러 프레임이라 "아직 안 때린 것 중 최근접"을 매 프레임 고르면 한 번 휘둘러 여러 명을 차례로 벤다 | 다중 타격은 스킬 플래그(`attack_multi`)로 해금 |
| 플래그 이름을 **인스펙터 문자열**로 | 기획이 스킬 구성을 바꿔도 코드가 안 따라가게 | 오타에 약하다 |
| **차지는 언제나 360° 광역** | 확정 예외. 해금과 무관 | |
| 자동 조준은 **스윙 시작 때 한 번만** | 액티브 동안 계속 겨누면 적을 따라 칼이 휘는 유도탄이 된다. 스펙은 "방향 보정"이지 추적이 아니다 | |
| 자동 조준은 **커서 쪽 ±60°** 안의 적만 | 뒤에 선 적까지 집으면 칼이 홱 돌아가 조작이 손에서 떠난다 | 차지는 겨누지 않음 (어차피 360°) |
| 스윙 시작 시 **조준 잠금을 먼저 내림** | 못 찾으면 손대지 않는데, 직전 스윙의 잠금이 남아 커서 조준이 영영 안 돌아온 적이 있다 | |
| 겨눌 때와 때릴 때 **같은 탐색 함수** (`FindNearestEnemy`) | 규칙이 다르면 "돌아봤는데 안 맞는다"가 생긴다 | |
| 피격·방패 시 **스윙·차지 즉시 취소** | `CanAttack`이 false면 `Update` 첫 줄에서 `CancelSwing` | 누른 채로 있으면 다음 프레임에 차지 모드가 다시 잡히는데, 게이지는 `GameInput`이 누른 순간부터 잰 값이라 **처음부터 다시 차지 않는다** |
| 공격력은 **장비에서만**, 버프는 % | 여기에 숫자를 박으면 무기 티어를 늘릴 때 코드를 고쳐야 한다 | 무기가 없으면 1 |
| `AttackPower`를 **스탯 창도 읽음** | 화면용 계산을 따로 두면 실제 피해와 어긋난다 | |
| 채집 간격 감소는 **최대 90%**, 최소 0.05초 | 100%면 간격 0 → 한 프레임에 광물이 사라진다 | |
| 탐색은 `OverlapSphereNonAlloc` + **32칸 버퍼** 재사용 | 매 프레임 도는 판정이라 GC 할당을 피한다 | 반경 안 콜라이더가 32개를 넘으면 일부가 빠진다 |
| 채집 대상만 **`RegionGate`로 거름** | 벽 너머 광물을 캐는 일이 실제로 나왔다 (2차 피드백) | 적 탐색은 안 거른다 |
| 뗀 순간 공격이 불가하면 **버림** (대기열 없음) | 입력 버퍼를 두면 의도치 않은 늦은 스윙이 나간다 | |

### 3-5. 방패와 체력

**한 줄**: 방패는 **각도만 답하고**, 막을지 말지와 피해 계산은 **`PlayerHealth` 한 곳**이 정한다.

`PlayerHealth.TakeDamage`의 판정 순서 (이 순서 자체가 결정이다):

```
1. 죽었음 / 0 이하       → 무시
2. 피격 무적 중          → 무시
3. 대시 무적 중          → 무시
4. 일반 공격 && 방패 각도 안 → Blocked 이벤트, 피해 없음
5. 피해 감소(%) 적용, 최소 1
6. 무적 시작 → 체력 감소 → 점멸 → 넉백 → Changed
7. 0 이하 → Died → 즉시 Respawn
```

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 방패는 **누르는 동안만** (토글 아님) | 확정 스펙 | |
| 각도 판정은 `PlayerShield.Blocks` **한 곳**, 막을지 최종 판단은 `PlayerHealth` | 조건이 두 군데로 갈리면 연출과 판정이 어긋난다 | |
| 방어불가 공격이면 **`Blocks`를 아예 안 부름** | `Blocks`는 성공하면 `Blocked` 이벤트를 쏜다. 불러두고 결과만 무시하면 막기 연출이 잘못 나간다 | |
| 공격원이 몸에 **겹쳐 있으면 막은 것**으로 | 방향을 계산할 수 없음 | 이때는 `PlayerShield.Blocked`가 안 나간다 |
| 막으면 **완전 차단** (무적 시간도 안 줌) | 앞서 확정된 쪽 | `_knockbackWhenBlocked`로 밀림만 켤 수 있다 |
| `Blocked` 이벤트에 **누구를 막았는지**(source) 실음 | "막히면 공격자가 잠깐 멈춘다" 규칙을 몬스터가 쓰려면 필요 | |
| 피해 감소는 **%를 먼저 더하고 한 번 곱함**, 최대 90% | 출처마다 곱하면 둘만 겹쳐도 체감이 과하게 세진다 | |
| **최소 피해 1** | 방어구만으로 무적이 되면 전투가 성립 안 함 (기획도 못박음) | |
| 피격 후 **무적 시간** | 연속 피격으로 즉사 방지 | 테스트 때 같은 프레임 연타가 전부 무시된다 (`ARCHITECTURE.md` 7절) |
| `MaxHp` = 기본 + 방어구 | 최대 체력을 묻는 곳이 전부 여기를 봐야 갑옷 낀 뒤 체력바가 옛 칸 수로 남지 않는다 | |
| 사망 = **즉시 리스폰 지점으로, 체력 가득** | 사양 2-2 | 같은 프레임에 `Changed`가 두 번(0 → 가득) |
| **죽음 패널티는 구현 안 함**, `Died` 이벤트만 열어둠 | 기획 미확정 (감소율·지속 시간 공란). 추측으로 채우지 않는다 | 확정되면 `Died`를 듣는 컴포넌트 하나 추가. 이 파일은 안 고침 |
| 저장 = **체력 + 위치** | | 체력은 최소 1로 복원 |
| 불러올 때 **겹치지 않는 가장 가까운 자리** 탐색 (8방향 × 4링) | 광물은 저장 안 하므로, 캔 자리에 서서 저장했다 불러오면 되살아난 광물 안에서 깨어날 수 있었다 (3차 피드백). 광물 쪽 "막히면 미룸"만으론 순서에 따라 뚫림 → **양쪽 다 막아 순서에 기대지 않음** | 전부 막히면 원래 자리 |
| 위치 복원 시 **Rigidbody에도 넣고 `SyncTransforms`** | transform만 옮기면 Rigidbody가 옛 자리로 되돌린다 (몬스터 순간이동과 같은 함정) | |
| 불러온 직후 **잠깐 무적** | 불러오자마자 맞지 않게 | |

### 3-6. 능력치 공급원 — 장비 · 버프 · 채집력

**한 줄**: 수치를 **쓰는 쪽은 공급원의 합산 프로퍼티만** 본다. 합치는 규칙은 쓰는 쪽(공격·체력)에 한 번.

| 공급원 | 가진 상태 | 내놓는 합 |
|---|---|---|
| `PlayerEquipment` | 슬롯 → 장비 | 채집력, 공격력, 피해 감소 %, 최대 체력 |
| `PlayerBuffs` | (버프, 남은 시간) 목록 | 채집 속도 %, 공격력 %, 피해 감소 % |
| `HarvestPower` | 스킬 보너스(정수) | 채집 피해 = 기본 + 도구 + 보너스 |

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 장비 수치를 **`PlayerEquipment` 한 곳**에서 합산 | 장비 종류마다 컴포넌트를 두면 합치는 곳이 흩어져, 세트 효과 같은 게 들어올 때 샌다 | |
| 장비는 **인벤토리에 안 들어감**. 낀 것 = 가진 것 | 확정: 되팔기·보관 불가 | 교체하면 **예전 것은 그냥 사라진다** |
| 교체 규칙은 **티어 비교 하나** (`CanEquip`) | 중복 불가·건너뛰기 허용·하향 금지가 전부 "지금보다 위인가"로 정리 | |
| 불러올 때는 **`Equip`을 거치지 않음** | 복원은 규칙을 다시 따질 일이 아니라 적힌 그대로 되돌리는 일 | |
| 같은 버프는 **쌓지 않고 시간만 채움** | 쌓는 규칙은 기획 미확정이고, 쌓이는 쪽이 되돌리기 어렵다 | |
| 버프 `Changed`는 **끝났을 때만** (매 프레임 X) | 매 프레임 알리면 듣는 쪽이 매 프레임 다시 그린다 | 남은 시간 표시는 듣는 쪽이 직접 폴링해야 한다 |
| 버프 남은 시간은 **올림한 정수 초**로 저장 | 소수점까지 적으면 매 프레임 글자가 달라져 자동 저장의 "바뀐 게 있나"가 늘 참 | |
| 저장 목록 **정렬** (장비·버프 모두) | 사전·리스트 순서가 실행마다 달라도 같은 문자열이 나오게 | |
| 채집력에서 **스킬 보너스(`Bonus`)를 도구 몫과 따로** 저장 | 섞으면 불러올 때 도구 수치가 두 번 들어간다 (장비도 따로 저장하므로) | |
| 버프는 채집 **위력이 아니라 속도** | 기획이 "광물 공격 간격 20% 감소"로 적음. `FromBuff`는 0으로 남겨둠 | |
| `BuffDefinition`을 **별도 파일**로 분리 | SO를 MonoBehaviour와 한 파일에 두면 재컴파일 때 에셋의 스크립트 참조가 끊길 수 있다 (실제로 `Buff_Strength`가 `m_Script: 0`이 되어 명부에서 사라짐) | **한 파일에 클래스 하나, 파일명 = 클래스명** |

### 3-7. 핫바와 E 키

**한 줄**: `QuickBar`는 **선택 상태만** 가진다. E 키 하나를 소모품 사용과 블럭 설치가 **아이템 종류로 나눠** 듣는다.

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 선택 상태를 **UI가 아니라 `QuickBar` 컴포넌트**에 | 상태가 UI 안에 있으면 설치 쪽이 UI를 참조하게 되고, UI를 갈아끼울 때 게임 로직이 깨진다 | 그리기는 `QuickBarView` |
| 핫바 = **인벤토리 앞 9칸**을 그대로 씀 | 별도 핫바 저장소가 없으니 동기화 문제가 없다 | 인벤 칸이 당겨지면([2-4](#2-4-아이템-데이터)) 핫바 내용도 바뀐다 |
| 휠 끝에서 **반대편으로 순환** | 마인크래프트와 같은 감각 | 숫자키 선택은 순환 없이 클램프 |
| **E = 고른 것을 쓴다** | 한 아이템이 블럭이자 소모품일 수는 없으니 부딪히지 않는다. 플레이어는 "E는 고른 것을 쓴다" 하나만 외우면 됨 | 두 컴포넌트가 같은 이벤트를 듣는다. 소모품을 고르고 E를 누르면 `BlockPlacer`도 `Rejected(NotPlaceable)`을 쏜다 (배너가 무시) |
| 소모품: **먼저 빼고 쓴다** | 반대로 하면 효과만 들어가고 개수가 안 줄어드는 순간이 생긴다 | |
| 블럭: **먼저 빼고 만든다** | 반대로 하면 빼기가 실패했을 때 블럭만 남아 복제가 된다 | |
| 블럭을 **만드는 일은 `PlacedBlocks`** | 저장에서 돌아올 때도 같은 길을 타야 한다 | |
| 거부 이유를 **enum `PlaceResult`**로 | 안내 문구를 붙일 때 이 값만 보면 된다 | |
| `Rejected`에 **아이템도 같이** 실음 | 사유만으로는 "이 구역엔 이미 있습니다"의 '이것'을 쓸 수 없다 | |
| 커서 칸은 **바닥 콜라이더가 아니라 그리드 원점 높이의 평면**에 레이 | 실제 콜라이더를 맞히면 구조물 윗면에 걸려 커서와 다른 칸이 잡힌다 | |
| 목표 칸·판정 결과를 **프레임당 한 번** 계산해 미리보기와 설치가 공유 | 미리보기는 초록인데 설치는 실패하는 어긋남 방지 | |
| 사거리는 **수평 거리** | 높이까지 섞으면 지형에 따라 사거리가 달라진다 | |
| 칸 점유는 `GridOccupancy`, **살아있는 것만 물리**로 | 생물은 그리드 레지스트리에 없다 | 확인 반경을 칸 반폭보다 작게 (옆 칸에 붙어 선 플레이어까지 걸리지 않게) |
| 구역당 제한 확인은 **제한 있는 아이템일 때만** 씬을 셈 | 미리보기 때문에 매 프레임 돈다. 평소 비용은 0이어야 한다 | 제한 있는 아이템을 들고 있으면 매 프레임 `FindObjectsByType` |
| 높이 오프셋은 **만드는 쪽(`PlacedBlocks`) 값**을 읽음 | 따로 두면 미리보기와 결과가 어긋난다 | |
| 크기는 **프리팹의 `GridPlacement.Size`**를 인스턴스 없이 읽음 | 2칸 구조물 대비 | 회전 설치는 아직 없음 |
| 미리보기 색은 **`MaterialPropertyBlock`** | 색만 바꾸려고 머티리얼을 복제하면 인스턴스가 샌다 | |

### 3-9. Player에서 반복되는 패턴 · 낡은 주석

**패턴**

| 패턴 | 어디서 |
|---|---|
| **행동은 자기 상태만 공개, 허용은 판정자에 묻기** | 모든 행동 컴포넌트 → `PlayerActionState` |
| **시각 비교로 상태 판단** (`Time.time < _xxxUntil`) | 대시, 무적, 채집 간격, 스윙 구간 |

| **화면과 실제 판정이 같은 값을 읽는다** | `AttackPower`(스탯 창), `CurrentResult`(미리보기), `MaxHp`(체력바) |
| **판정에 쓰는 버퍼는 재사용** (`NonAlloc`) | `PlayerAttacker`, `BlockPlacer`, `PlayerHealth` |
| **기획 미확정은 이벤트 · 스위치만 열어둠** | `Died`(죽음 패널티), `_invulnerableTime`(무적 대시), `_knockbackWhenBlocked` |

**코드와 안 맞는 주석** (고칠 때 같이 정리할 것)

- `PlayerMotor` 머리말의 `PlayerHarvester` → 지금 이름은 `PlayerAttacker`.
- `HarvestPower` 머리말 "상점 아이템 효과가 건드리는 유일한 지점" → 지금은 장비·스킬이 건드리고, 상점은 안 건드린다.
- `PlayerActionState` 머리말의 우선순위에 "경직"이 있지만 플레이어에는 경직 상태가 없다.

## 4. Data

`Data`라는 폴더는 없다. 여기서 말하는 데이터 레이어는 **폴더를 가로지르는 두 반쪽**이다.

### 4-0. 두 반쪽: 정의와 상태

```
 정의 (ScriptableObject 에셋)                     상태 (MonoBehaviour 컴포넌트)
 "무엇이 있는가" — 디자이너가 만든다               "지금 어떤가" — 플레이하며 바뀐다
 ─────────────────────────────────               ─────────────────────────────────
 ItemDefinition  Mineral_Iron.asset      ◄─참조─  Inventory      [철 ×12, 구리 ×5]
 EquipmentDefinition  Tool_Iron.asset    ◄─참조─  PlayerEquipment {Tool: Tool_Iron}
 SkillDefinition  Skill_Harvest.asset    ◄─참조─  SkillBoard     learned = {Skill_Harvest}
 RegionDefinition  Region_Rocks.asset    ◄─참조─  RegionAccess   unlocked = {Region_Rocks}
 ShopGood  Good_Bag1.asset               ◄─참조─  ShopStation    bought = {Good_Bag1}
           │                                               │
           │ 플레이 중 절대 안 바뀜                          │ Changed 이벤트 → UI
           ▼                                               ▼ Capture → 이름 목록 → 저장 파일
       빌드에 포함                                     SaveCatalog 로 이름 → 에셋 복원
```

**규칙 하나**: 에셋에는 **진행 상태를 절대 넣지 않는다.** 상태는 그 에셋을 참조하는 컴포넌트가 든다.

**왜**: 에디터에서 플레이할 때 SO 필드를 바꾸면 **에셋 파일 자체가 바뀌어** 플레이를 멈춰도 남는다.
"배운 스킬", "산 품목", "연 구역"을 에셋에 넣으면 다음 플레이에 이미 배운 채로 시작한다.
이 함정을 구역 · 스킬에서 실제로 겪었고, 그 뒤로 모든 정의 클래스 머리말에 같은 경고가 붙어 있다.

### 4-2. 종류를 늘리는 세 가지 방법

같은 "종류가 늘어난다"에도 코드는 세 가지 다른 모양을 쓴다. **어느 것을 고를지가 곧 설계 결정**이다.

| 방법 | 쓰는 곳 | 언제 고르나 | 쓰는 쪽 코드 |
|---|---|---|---|
| **① 상속** | `ItemDefinition` → `Mineral` / `Consumable` | 종류마다 **동작 자체가 다르고**, 쓰는 쪽이 "이건 무슨 타입이냐"로 갈라야 할 때 | `if (item is ConsumableDefinition c)` |
| **② 값(enum·숫자)으로 가르기** | `EquipmentDefinition.Slot`, `Tier` | 종류 간 차이가 **"어느 자리 / 어느 수치"뿐**일 때 | 분기 없음. 값만 읽는다 |
| **③ 추상 효과 에셋 목록** | 소모품 효과, 상점 효과, 스킬 효과, 구역 조건, 몬스터 공격 | **기획이 무엇을 들고 올지 모를 때.** 한 정의가 효과를 여러 개 조합할 때 | `foreach (effect) effect.Apply(ctx)` — 새 종류가 와도 안 고침 |

**고른 이유 (각 클래스 주석에서)**

- 소모품은 ① — 광물까지 "쓸 수 있는 것"이 되면 E를 눌렀을 때 아이템마다 따져야 한다. 타입으로 가르면 "소모품이냐"만 물으면 된다.
- 장비는 ② — 도구·무기·방어구를 클래스로 나누면 장착·구매·저장이 세 갈래가 된다. 장비 전용 특수 능력이 생기면 그때 ③으로 뺀다.
- 몬스터 공격은 ③ — "유형"이란 결국 공격 조합이다. 수치 필드로 적으면 근접 + 투사체를 둘 다 가지는 순간 필드를 통째로 복제해야 한다.

**③을 쓸 때 따라오는 짝**

| 부품 | 역할 |
|---|---|
| `Apply(ctx)` / `Use(ctx)` / `Execute(ctx)` / `IsMet(ctx)` | 본 동작 |
| `Describe()` | 자기 설명 문구. UI가 `if`를 쌓지 않고 그대로 띄운다 |
| `CanUse` / `CanBuy` (+ `out reason`) | 지금 가능한가 + 안 되는 이유. 기본값은 "가능" |
| `XxxContext` | 효과가 건드릴 수 있는 시스템 묶음. 효과가 시스템을 직접 찾아다니지 않게 |
| `Consume` / `HasCost` (구역 조건만) | 치르는 조건과 자격만 보는 조건을 가름 |

### 4-3. 정의 쪽 결정

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| **정의 = SO, 상태 = 컴포넌트** ([4-0](#4-0-두-반쪽-정의와-상태)) | 에디터 플레이가 에셋을 오염시키지 않게 | 직렬화되지 않는 캐시 필드는 괜찮다 (`SaveCatalog._byName` — `[SerializeField]`가 없는 private 사전) |
| 필드는 `[SerializeField] private`, 밖에는 **읽기 전용 프로퍼티** | 런타임 코드가 정의를 고칠 길을 막는다 | |
| **범위 보정을 프로퍼티에서** (`Mathf.Max(1, _maxHp)`) | 디자이너가 0이나 음수를 넣어도 게임이 안 깨진다. `OnValidate`로 값을 고치지 않고 읽을 때 보정 | 인스펙터에 보이는 값과 실제 값이 다를 수 있다 |
| 표시명이 비면 **에셋 파일명** | 한 군데만 고쳐도 되게 | 파일명은 **영문 강제** (한글 리터럴 깨짐 사고) |
| 정의가 **자기 겉모습**을 든다 (아이콘, 대표색, 드랍/설치 프리팹, 벽 프리팹) | 아트 교체가 에셋 수정으로 끝난다. 아이콘이 없을 때는 `UiColor`가 칸 색을 대신 | 대표색은 **종류마다 고정** — 획득 순서로 색을 배정하면 먼저 캔 광물이 남의 색을 뒤집어쓴다 (팀 리뷰) |
| 몬스터는 **정의가 프리팹을 든다** (프리팹이 정의를 드는 게 아니라) | 같은 몸통 하나를 구역별 정의 여럿이 돌려 쓴다. 기획: "형태를 유지하되 색으로 구분" | 몸 색은 `MaterialPropertyBlock` — 머티리얼을 종류 × 구역만큼 만들지 않으려고 |
| **파생 수치는 저장하지 않고 계산** (`Dps`, `RetreatRange`, `MaxAttackRange`, `Summary`) | 따로 적으면 원본과 어긋난다. "안 쏘는 거리"와 "물러나는 거리"가 다르면 멍하니 서 있는 구간이 생긴다 | 밸런스 표가 이 계산 값을 열로 보여준다 |
| 스킬 이웃은 **목록이 아니라 좌표에서 계산** | 이웃을 적어두면 격자를 고칠 때마다 주변을 전부 다시 적어야 한다. 좌표면 노드를 옮겨도 연결이 따라온다 | 격자 조회가 선형 탐색 (노드 수가 작아 무시) |
| 시작 스킬은 **좌표가 아니라 별도 목록** | "중앙"을 좌표로 못박으면 격자를 옮길 때마다 코드가 따라가야 한다 | |
| 상점 순서는 **선행 품목 참조**(`_requires`) | 가방 확장 2단계처럼 순서 있는 품목. 목록 순서나 레벨로 거르지 않음 | 순환 참조를 만들면 둘 다 영영 안 뜬다 |
| 제작 결과는 **장비 or 아이템 중 하나만** 채우기로 함 | 두 종류의 수령 방식이 다르다 (장비는 바로 장착, 아이템은 가방 or 바닥) | 검증 코드는 없다. 둘 다 채우면 **둘 다 지급**된다 (장착 후 아이템). 인스펙터 머리말로만 안내 |
| 제작대·상점 분류는 **문자열** | 보스 전용 제작대도 "분류가 다른 제작대"일 뿐 | 오타에 약하다 |
| 버프·장비 수치는 **같은 축**으로 맞춤, 버프는 전부 **%** | 합산하는 자리가 늘면 안 된다. "증가율을 다 더한 뒤 한 번 곱" | |
| 몬스터 처치 경험치는 **수치를 남기고 토글로 끔** | 수치를 지우면 되살릴 때 균형값을 다시 잡아야 한다 | `CombatRewardService._grantExpOnKill` |
| 장비 상점가 **0 = 비매품** | 도구는 제작 전용이라 가격 칸을 비워 표시 | 상점 품목(`ShopGood`)의 가격과는 별개 |
| **SO와 MonoBehaviour를 한 파일에 두지 않음**, 파일명 = 클래스명 | 한 파일에 두면 재컴파일 때 에셋의 스크립트 참조가 끊길 수 있다 (`Buff_Strength`가 `m_Script: 0`이 되어 명부에서 사라짐) | |

### 4-4. 에셋 현황과 이름 규칙

| 폴더 | 접두사 | 개수 | 내용 |
|---|---|---|---|
| `Items/` | `Mineral_` | 5 | 돌 · 철 · 은 · 금 · 수정 |
| | `Item_` | 3 | 회복약, 버프약(소모품), 보관함(설치물) |
| | `Use_` | 2 | 소모품 효과 (회복, 힘) |
| | `Monster_` | 2 | ⚠️ 옛 슬라임 정의 — [4-8](#4-8-정리하다-걸린-것) |
| `Equipment/` | `Tool_` `Weapon_` `Armor_` | 4 · 4 · 2 | 도구는 제작, 무기·방어구는 상점 |
| `Buffs/` | `Buff_` | 1 | 힘 |
| `Recipes/` | `Recipe_` | 5 | 도구 4 + 보관함 |
| `Shop/` | `Good_` | 9 | 상점 품목 |
| | `Shop_` | 9 | 상점 **효과** (품목 아님) |
| `Monsters/` | `Monster_<종류>_R<구역>` | 13 | 돌무더기 · 투척꾼 · 돌격꾼 · 골렘, 구역별 강화판 |
| | `Attack_<종류>_R<구역>_<동작>` | 17 | 위 몬스터들의 공격 |
| `Regions/` | `Region_` | 3 | 들판 · 바위 지대 · 수정 굴 |
| | `Require_` | 4 | 입장료 400 / 1200 / 3000 / 7000 (뒤 둘은 땅이 아직 없음) |
| `Skills/` | `SkillTree` | 1 | 격자 |
| | `Skill_` | 13 | 노드 (`Skill_Node_*`은 자리만 잡은 더미) |
| | `Effect_` | 2 | 스킬 효과 (채집력, 다중 타격) |

**이름 규칙 정리**

- 파일명은 **영문 + `종류_이름`**. 저장 파일에 이 이름이 그대로 적히므로 **한 번 정하면 바꾸지 않는다** (바꾸면 옛 세이브에서 그 항목이 사라짐).
- 이름은 프로젝트 전체에서 **유일**해야 한다 (같은 타입이 아니어도). 명부 인스펙터가 겹치는 이름을 빨갛게 띄운다.
- 몬스터는 **같은 종류의 구역별 강화판을 `_R<n>`으로** 구분한다. 기획 방침이 "구역마다 새 몬스터가 아니라 같은 몬스터의 강화판을 색만 바꿔 돌려쓴다"이기 때문.
- 효과 접두사가 묶음마다 다르다: 소모품 `Use_`, 상점 `Shop_`, 스킬 `Effect_`, 구역 조건 `Require_`, 몬스터 `Attack_`.

**공통 모양** — 새 상태 컴포넌트를 만들면 이걸 따른다:

```csharp
public class Xxx : MonoBehaviour, ISaveable            // + ISaveMilestone / ISaveSummary (선택)
{
    public event Action<Xxx> Changed;
    void Awake()  { /* 시작값 */ }
    void Start()  => Changed?.Invoke(this);              // UI가 첫 값을 받도록 한 번
    public void Mutate(...) { /* 바꾸고 */ Changed?.Invoke(this); }

    [Serializable] class Save { ... }                    // 저장 모양은 private 중첩 클래스
    public string SaveKey => "xxx";                      // 한 번 정하면 불변
    public string Capture() { /* 목록은 정렬, 시간은 정수 */ }
    public void Restore(string json) { /* 범위 보정, 사라진 에셋은 건너뜀 */ Changed?.Invoke(this); }
}
```

### 4-6. 상태 쪽 결정

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 상태 컴포넌트는 **아무것도 참조하지 않고 `Changed`만 쏨** (가방·골드·레벨·채집력) | UI를 통째로 바꾸거나 시스템을 추가해도 데이터는 안 건드린다 (`ARCHITECTURE.md` 3-1) | `HarvestPower`는 예외 — 장비·버프를 읽어 합산한다 |
| 첫 `Changed`를 **`Start`에서** | `Awake`에서 쏘면 아직 구독 안 한 UI가 놓친다 | `HudView` 등 일부 UI는 `OnEnable`에서 현재 값으로 한 번 더 맞춘다 (이중 안전) |
| 값이 **실제로 바뀔 때만** 이벤트 | 0을 더하거나 같은 기록을 다시 세우면 구독자가 두 번 반응한다 | `ProgressFlags.Raise`는 이미 있으면 조용히 끝 |
| **잔액 확인과 차감을 한 함수로** (`TrySpend`) | "차감 성공했을 때만 효과 적용"을 한 줄로 보장 | 0원 차감은 지금도 false. 상점 0골드 품목이 막히던 원인이었고, `ShopStation.TryBuy`가 0원이면 차감을 건너뛰도록 고쳤다 |
| 가방 규칙은 **`ItemContainer`**, `Inventory`는 껍데기 | 보관함이 같은 규칙을 쓴다 ([2-4](#2-4-아이템-데이터)) | |
| `Inventory.Items`는 **지연 생성** | 다른 컴포넌트의 `Awake`나 에디터 도구가 먼저 건드린다. 그때 null이면 조용히 0개로 보여 추적이 어렵다 | |
| 넘친 아이템은 **버리지 않는다** — 돌려줄 땐 바닥에, 살 땐 미리 막음 | 확정 규칙 | 캔 자원은 애초에 바닥에 떨어지고, 못 주우면 수명이 다해 사라진다 |
| 레벨업은 **`while`로 연속 처리, 초과분 이월** | 사양 1-5 | 최대 레벨이면 `ExpToNext = 0`, UI가 `-`로 표시 |
| 경험치만 오른 건 **큰 사건이 아님**, 레벨업만 | 레벨업은 스킬 포인트를 주므로 되돌리기 어렵다 | |
| 진행 기록은 **문자열 하나** (전용 클래스 없음) | 기획이 어떤 사건을 조건으로 삼을지 모른다. 디자이너가 에셋에 적는 것만으로 새 조건이 생긴다 | 오타에 약하다. 쓰는 곳: 스킬 효과(쓰기), 구역 조건 · 다중 타격(읽기) |
| 플레이 시간은 **unscaled**로 셈 | 일시정지·슬로모션에 따라 늘었다 줄었다 하면 "몇 시간 했지"에 답이 안 된다 | |
| 슬롯 요약 순서는 **숫자**(`SummaryOrder`: 0 레벨 · 10 시간 · 20 골드) | 글자로 정렬하면 순서가 뒤집힌다 | |
| 일부 상태는 **필드가 아니라 씬에서 읽음** (`MonsterDeaths`, `PlacedBlocks`) | 목록을 따로 들면 씬과 어긋난다. 씬이 진실 | 저장할 때마다 `FindObjectsByType` |

### 4-7. 정의 ↔ 상태 ↔ 저장

```
저장할 때   상태 ─ SaveCatalog.NameOf(asset) ─► "Tool_Iron"  ─► save_0.json
불러올 때   save_0.json ─► "Tool_Iron" ─ catalog.Find<EquipmentDefinition>() ─► 에셋 ─► 상태
```

- 명부(`SaveCatalog.asset`)는 지금 **49개**. 인스펙터의 **"프로젝트에서 다시 긁어오기"** 버튼이
  `ItemDefinition` · `EquipmentDefinition` · `CraftRecipe` · `ShopGood` · `BuffDefinition` · `SkillDefinition` · `RegionDefinition`을 자동 수집한다 (`Editor/SaveCatalogEditor.cs`의 `Kinds`).
- **새 아이템·장비·스킬·구역을 만들면 버튼을 한 번 눌러야 한다.** 안 누르면 그 에셋은 불러올 때 조용히 사라진다.
- **새 정의 타입을 저장 대상으로 만들면** `Kinds`에 타입 이름을 추가해야 한다.
- 명부에 없어도 되는 것: 몬스터(칸 좌표로 저장), 공격·효과·조건(정의의 부품), `SkillTree`, `MapPalette`.

**불러올 때 효과를 다시 적용하지 않는다** — 스킬 효과, 상점 효과 모두.
효과의 **결과**가 이미 다른 상태에 저장돼 있기 때문이다 (스킬 → `harvestPower`·`flags`, 상점 → `inventory`·`equipment`).
다시 적용하면 두 번 들어간다. 그래서 `HarvestPower`도 도구 몫과 스킬 몫을 따로 저장한다.

### 5-1. 죽어도 사라지지 않는다 — 존재 끄기

World 전체를 꿰는 첫 번째 결정이다. 광물 · 몬스터 · 구역 벽은 **죽거나 열려도 `GameObject`를 끄거나 지우지 않고, 렌더러와 콜라이더만 끈다** (`SetPresence(false)`).

| 왜 | |
|---|---|
| **코루틴이 살아야 한다** | `SetActive(false)`면 그 오브젝트의 부활 코루틴이 같이 죽는다 |
| **참조가 유효해야 한다** | 보상 서비스 · 피드백 · 체력바가 시작할 때 한 번 모은 참조를 끝까지 쓴다 ([2-3](#2-3-보상-서비스)) |
| **다시 켤 수 있어야 한다** | 벽을 다시 잠그는 기획이 오면, 꺼진 오브젝트의 컴포넌트는 깨어나지 못한다 |
| **풀링이 필요 없다** | 고정 배치물은 생성/파괴가 없으니 풀 대상이 아니다 ([2-6](#2-6-오브젝트-풀)) |

| 대가 · 주의 | |
|---|---|
| 몬스터는 죽은 동안 **Rigidbody를 kinematic**으로 | 콜라이더가 꺼져 바닥을 못 받치는데 중력은 그대로라, 대기 시간 내내 맵 아래로 떨어졌다 (`ARCHITECTURE.md` 6절) |
| `Update`/`FixedUpdate`는 계속 돈다 | 각 컴포넌트가 `IsAlive`로 직접 막아야 한다 (`MonsterAI` 첫 줄) |
| 예외: **설치한 광물 블럭은 캐면 `Destroy`** | 칸이 비어야 다음 설치가 된다 |

### 5-2. 광물 — `MineralNode`

**한 줄**: 수치는 정의에서, 보상은 이벤트로. 노드는 **체력과 존재**만 관리한다.

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 보상을 **직접 주지 않고 `Harvested`만** 쏨 | 처리 순서는 `HarvestRewardService`가 소유 ([2-3](#2-3-보상-서비스)) | |
| 이미 깨진 광물에 추가 타격은 **무보상** | 예외 1-10 | |
| 한 번에 깎이는 양은 **최소 1** | 채집력이 0이어도 캘 수는 있게 | |
| `Destroy`는 **이벤트 뒤에** | 먼저 지우면 구독자가 노드 위치를 못 읽어 드랍이 엉뚱한 데 떨어진다 | |
| 부활 자리에 생물이 있으면 **미룸 (건너뛰지 않음)** | 그냥 켜면 콜라이더가 겹친 상대를 광물 위로 밀어 올린다. 건너뛰면 그 칸의 광물이 영영 안 돌아온다 | 0.5초 간격으로 재확인 |
| **즉시 부활(`Respawn()`)도 같은 검사** | 시간 경로만 막았더니 불러오기·디버그 같은 "즉시" 경로가 검사를 건너뛰어 플레이어 몸 안에서 광물이 켜졌다 (3차 피드백) | |
| 방해물은 **생물(`IDamageable`)만** 봄 | 다른 광물·구조물은 같은 칸에 놓일 수 없다 (`GridOccupancy`) | |
| 겹침 검사 크기는 **`Awake`에서 기억** | 콜라이더가 꺼진 뒤엔 `bounds`를 믿을 수 없다 | |
| 설치 블럭은 **`MarkAsPlaced()`** 한 번으로 경험치 X · 부활 X · 캐면 파괴 | 부활하면 무한 복제, 경험치까지 나오면 무한 파밍 | |
| 정의가 비면 **`LogError` + 비활성 상태** | 조용히 아무 일도 안 일어나는 것이 제일 나쁘다 | |

### 5-3. 바닥 드랍 — `DropService` · `ItemDrop`

**한 줄**: 캔 자원은 **바닥에 떨어지고 F로 줍는다.** 줍기는 기존 상호작용 경로를 그대로 탄다.

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 드랍이 **`IInteractable`** | "구리 ×2 줍기" 프롬프트가 상점·변환기와 같은 방식으로 자동으로 뜬다. 새 입력·UI가 필요 없다 | 줍기도 2m 최근접 하나 |
| **수명(30초) + 개수 상한(100)** 둘 다 | 한 번에 왕창 떨어지면 수명이 다하기 전에 쌓인다. 무한히 쌓이면 상호작용 탐색 비용이 계속 는다 | 상한을 넘으면 가장 오래된 것부터 치움 |
| 활성 목록은 **오래된 순**, `Update`는 앞에서부터 보다가 멈춤 | 매 프레임 전체를 훑지 않는다 | |
| 만료 시각은 **드랍이 아니라 서비스의 사전**에 | 드랍에 들리면 풀에서 재사용될 때 옛 값이 따라다녀 꼬인다 | |
| **드랍은 저장하지 않고, 불러올 때 전부 치움** | 안 치우면 인벤만 과거로 돌아가고 바닥 것은 남아, 그걸 주우면 복제가 된다 (3차 피드백에서 실제로 나옴). 30초짜리를 저장할 가치는 없다 | 저장 직전에 캔 자원은 불러오면 사라진다 |
| 가방이 꽉 차면 **일부만 줍고 나머지는 바닥에** | 확장 2-4 | |
| 종류별 모양(`DropPrefab`) 없으면 **기본 프리팹** | 아트가 없어도 동작 | |
| 아트 프리팹에 **빠진 부품을 채움** (`ItemDrop`, 트리거 콜라이더) | 아트가 준 모델을 그대로 꽂아도 동작하게. 콜라이더가 없으면 영원히 못 줍는다 | 콜라이더는 **트리거로 강제** (길을 막지 않게) |
| 색은 **`MaterialPropertyBlock`** | 머티리얼 공유 | |
| **`GiveOrDrop`**: 가방에 넣고 넘친 만큼 바닥에 | 돌려주는 자리(제작 수령·취소)는 "못 넣으면 막는다"가 답이 아니다. 취소를 못 하면 슬롯이 영영 묶이고, 버리면 재료가 증발한다 | |
| 드랍 생성은 **`PoolManager`** | 자주 생기고 사라짐 | 반납 시 `PickedUp = null`로 구독 정리 |

### 5-4. 설치 블럭 — `PlacedBlocks` · `PlacedBlock` · `StorageBox`

**한 줄**: 블럭은 **한 길로만 생긴다**(`PlacedBlocks.Place`). 놓기와 불러오기가 같은 길을 탄다.

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 생성을 `BlockPlacer`에서 **떼어 `PlacedBlocks`로** | 블럭은 두 경로(E로 놓기, 저장에서 복원)로 생긴다. 각자 만들면 한쪽만 고치는 사고가 난다 | |
| 저장할 때 **목록을 들지 않고 씬을 훑음** | 목록을 들면 "씬"과 "목록" 둘이 진실을 주장한다. 블럭이 다른 이유로 사라지는 경로(몹이 부숨, 에디터에서 지움)가 생기는 순간 저장이 조용히 틀린다 | 저장마다 `FindObjectsByType`. 몇 분에 한 번이라 괜찮다 |
| **`PlacedBlock` 표식** | 맵에 원래 있던 구조물과 플레이어가 놓은 것을 구분. `GridPlacement`만으로는 둘이 같다 | |
| 블럭의 추가 상태는 **`IBlockState`** (별도 `ISaveable` 아님) | 블럭 복원과 내용 복원이 서로 다른 저장 항목이면 순서가 보장되지 않아 "아직 없는 블럭에 내용을 넣는" 경우가 생긴다. **블럭과 그 내용은 한 덩어리** | 보관함 내용은 `placedBlocks` 항목 안에 같이 들어간다 |
| 불러올 때 **`DestroyImmediate`로 먼저 비움** | `Destroy`는 프레임 끝에 돈다. 그 사이 새 블럭을 놓고 다시 훑으면 옛 것이 잡혀 두 배가 된다 | |
| 사라진 아이템의 블럭만 **건너뜀** | 아이템 하나 정리했다고 깔아둔 게 통째로 날아가면 안 된다 | |
| 광물 블럭은 생성 시 **`MarkAsPlaced` + `Track`** | 시작 뒤 생긴 노드라 보상 서비스가 모른다 | |
| 보관함은 **상자마다 자기 컨테이너** + 구역당 1개 제한 | 결과적으로 "구역별 창고". 구역 키 공용 저장소로 만들면 상자를 부수고 다시 놓았을 때 내용이 어디 있어야 하는지 애매해지고, 저장도 블럭과 따로 떨어진다 | |
| 보관함은 **명부(`SaveCatalog`)를 프리팹이 직접** 듦 | 에셋 참조라 프리팹이 들 수 있다 (씬 참조는 불가) | 비어 있으면 경고 후 복원 생략 |
| 보관함은 **화면을 모름** (`OpenRequested`만) | 스테이션 공통 규칙 | 컨테이너의 `Changed`를 다시 쏘지 않는다 → 패널이 직접 다시 그림 |

### 5-5. 구역 벽 — `RegionBarrier`

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| **문이 없다.** 둘레 어디서든 F로 연다 | 입구를 한 곳으로 몰면 조건을 채우고도 입구를 찾아 둘레를 돌아야 한다 | |
| 열렸는지는 **`RegionAccess`에 묻기만** | 개방 상태의 주인은 하나 ([2-8](#2-8-구역)) | |
| 안내 문구는 **조건의 `Describe()`** | 조건 종류별 분기가 벽에 없다 | |
| 열리면 **존재만 끔** ([5-1](#5-1-죽어도-사라지지-않는다--존재-끄기)) | 다시 잠그는 기획이 오면 깨어나야 한다 | |
| 에디터 도구가 **경계를 따라 자동으로 두름**, 결과는 평범한 씬 오브젝트 | 런타임 생성 금지. 디자이너가 옮기고 지울 수 있다 | |
| 잠긴 구역 안에서도 **벽만은 상호작용 가능** | 벽을 막으면 구역을 여는 길이 사라진다 (`PlayerInteractor`) | |

| **화면을 모름** (`OpenRequested`) | 제작대가 UI를 참조하면 화면을 갈아끼울 때 따라 깨진다 | |

### 5-7. 몬스터 몸 — `Monster`

**한 줄**: `Monster`는 **체력 · 생사 · 부활**만. 이동과 공격은 `MonsterAI`.

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 몸(`Monster`)과 두뇌(`MonsterAI`) **분리** | 책임 분리. 보상·체력바·저장은 몸만 알면 된다 | |
| `Damaged`에 **깎인 양과 때린 쪽**을 실음 | 남은 체력으로 역산하면 여러 마리일 때 어긋난다. AI는 경직에, 연출은 데미지 숫자에 쓴다 | |
| `Damaged`를 **사망 판정보다 먼저** | 죽는 타격도 예고(윈드업)를 끊어야 한다 | |
| `kind`(방어불가)는 **무시** | 몬스터는 막는 수단이 없다. 인터페이스만 맞춤 | |
| 처치 보상은 **`Died` 이벤트로** | `CombatRewardService`가 받음. 드랍 아이템은 기획 미확정이라 안 만든다 | |
| 집 위치는 **`Start`에서** | `GridPlacement`가 `OnEnable`에서 위치를 맞추므로 `Awake` 값은 배치 전 좌표일 수 있다 | |
| 순간이동은 **Rigidbody 위치·속도 + transform + `SyncTransforms`** | transform만 옮기면 Rigidbody가 옛 자리로 되돌린다 | 플레이어 불러오기에도 같은 함정 |
| 불러오기용 **`MarkDeadSilently()`** | `Die`를 부르면 처치 보상과 떠오르는 숫자가 불러올 때마다 다시 나간다 | |
| 낙하 구제는 **`ReturnHome()`** (체력 유지) | 맵 밖으로 빠진 건 죽은 게 아니다 | |
| 종류 교체 **`Configure(def)`는 활성화 전에** | `Awake`가 정의에서 체력을 잡는다 | 스포너가 비활성 생성 → `Configure` → 켜기 순서를 지킨다 |
| 몸 색은 **`MaterialPropertyBlock`** | 구역 수만큼 머티리얼이 늘면 아트가 색을 바꿀 때 전부 다시 만들어야 한다 | 피격 점멸(`HitFlash`)이 같은 블록을 쓴다 — 서로 지우지 않게 주의 (고쳐짐) |

### 5-8. 몬스터 두뇌 — `MonsterAI`

**한 줄**: 상태 기계라기보다 **우선순위 사다리**다. 매 `FixedUpdate` 위에서부터 처음 걸리는 칸 하나만 실행한다.

```
 1. 정의 없음 / 죽음 / 표적 없음     → Idle
 2. 낙하                             → ReturnHome
 3. 돌진 중                          → Lunge       ← 위치를 직접 쥐는 구간이라 최우선
 4. 경직 중                          → (아무것도)
 5. 넉백 중                          → (아무것도)  ← Knockback이 위치를 쥠
 6. 빈틈(후딜) 중                    → Recover     ← 플레이어의 반격 창
 7. 예고 중                          → Windup      → 끝나면 Fire
 8. 집에서 너무 멂 (leash)           → Return
 9. 탐지 밖 / 다른 구역              → Return or Idle
10. 너무 가까움 + 물러날 수 있음     → Retreat
11. 쓸 수 있는 공격 있음             → Attack (Begin)
12. 사거리 안인데 전부 대기 중       → 제자리
13. 그 외                            → Chase
```

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| **사다리**(if 순서) 방식 | 전이표보다 읽기 쉽고, "무엇이 무엇을 가로채는가"가 순서 그 자체 | ⚠️ 순서를 바꾸면 동작이 통째로 바뀐다. 주석에 "따로 손볼 예정, 건드릴 때 순서를 먼저 확인" |
| 경로 탐색 = **직선** (`MoveTowards`) | 장애물이 드물어 NavMesh 굽는 비용이 더 크다 | 구조물에 끼기 시작하면 이 함수 하나만 `NavMeshAgent`로 |
| 이동은 **`MovePosition`** | 콜라이더를 밀어내며 이동해 구조물을 관통하지 않는다 | |
| **무엇을 쓸지는 정의의 공격 목록이 정함** | 공격 종류가 늘어도 이 파일은 안 는다 | |
| 공격 우선순위 = **목록 순서** | 코드가 아니라 디자이너가 정한다 | 원거리 → 근접 → 접촉 순으로 놓는 게 보통 |
| **쿨다운은 공격마다 따로** | 하나로 묶으면 근접을 쓴 뒤 원거리까지 같이 잠긴다 | |
| 쿨다운은 **내지른 순간부터** | 예고 시작부터 세면 예고가 긴 공격이 사실상 더 자주 나간다 | |
| 쿨다운(재사용) ≠ **빈틈**(아무것도 못 함) | 다른 축이다. 기획이 몬스터마다 예고와 빈틈을 따로 적었다. "막거나 피하면 잠시 멈추니 반격" | |
| 예고 중엔 **제자리** | 쫓아가며 때리면 예고가 피할 시간이 못 된다 | |
| 맞으면 **경직** → 예고 취소 + 돌진 정지 | 확정: 넉백을 hitstun으로 승격. 없으면 연타로 녹이는 동안에도 몹이 제 박자대로 때린다 | 경직은 넉백보다 살짝 길게 (밀리는 동안 쌓인 예고가 끝나자마자 터지지 않게) |
| 막히면 **몬스터가 스스로 듣고 멈춤** (`PlayerHealth.Blocked`) | 플레이어가 몬스터를 찾아 때리는 대신 몬스터가 "내 공격이 막혔나"를 듣는다. 플레이어가 몬스터를 알 필요가 없다 | 모든 AI가 구독하고 공격원이 **자기 자식**인지로 거른다 → 투사체는 걸러짐 |
| 표적 조건에 **같은 구역** | 벽 너머 플레이어를 쫓았다 (3차 피드백). 시야 레이캐스트는 광물·구조물 뒤까지 놓쳐 더 넓게 바뀐다. 구역 판정은 그런 오작동이 없다 | 구획 밖 몬스터는 이 규칙 면제 (아니면 영영 아무도 안 쫓음) |
| `HomeRegion`은 **값이 설 때까지 다시 물음** | 같은 오브젝트 안의 `Start` 순서가 보장되지 않아 먼저 읽으면 원점의 구역을 본다 | |
| 물러나기는 **자기 구역을 벗어나면 안 함** | 기획 "구역 밖으로 이동하지 않는다". 안 막으면 벽까지 밀린다 | |
| 물러날 거리 = **공격들의 최소 사거리 중 최대** | "안 쏘는 거리"와 "물러나는 거리"가 어긋나면 멍하니 서 있는 구간이 생긴다 | |
| 사거리 안인데 전부 대기 중이면 **제자리** | 더 다가가면 원거리 몬스터가 코앞까지 붙는다 | |
| 돌진은 **공격이 부탁하고 AI가 움직임** (`BeginLunge`) | 위치를 쥐는 곳이 둘이 되면 넉백·경직과 누가 몸을 옮기는지가 흐려진다 | 빈틈 타이머가 돌진 시작 때 걸려 돌진 시간과 겹친다 |
| 돌진은 **한 번만 맞히고, 벽이면 멈춤** | 뚫고 지나가면 구역 밖으로 나간다 | |
| leash는 **집에서의 거리** | 구역 개념 전의 대체. 구역이 들어오면 "구역을 넘었나"로 바꿀 자리 | |
| `Telegraphing` / `Lunged` 이벤트는 **아무도 안 들음** | 예고가 기획에 있는지 미확인. 이음새만 뚫어둠 | 예고 시간 0이면 이벤트도 안 나가 동작 그대로 |

### 5-9. 몬스터 공격 — `MonsterAttack` · `Projectile`

**한 줄**: **"몬스터 유형" = 공격 에셋 조합.** 유형을 enum이나 클래스로 만들지 않는다.

| 공격 | 하는 일 | 특이점 |
|---|---|---|
| `MeleeAttack` | 바로 때림 | 예고가 있었으면 **때리는 순간 사거리 재확인** — 피했는데 맞으면 예고가 신호가 아니게 된다 |
| `ContactAttack` | 몸통 닿음 피해 | 물리 충돌이 아니라 **공격 하나로** — 수치·방패·쿨다운을 같은 자리에서 읽고, **빈틈 동안엔 닿아도 안 아프다** (반격 창 보장). 목록 맨 아래 + 몸 반경 사거리 |
| `LungeAttack` | 예고 뒤 직선 돌진 | 방향은 **예고 끝난 순간에 굳힘** — 달리며 꺾으면 옆으로 피할 수 없다 (기획 명시). 사거리 = 언제 시작, 거리 = 얼마나 가나 |
| `ProjectileAttack` | 투사체 N발 부챗살 | 명중은 **날아가는 쪽이** 정함 — 발사 시점에 정하면 피할 수 없다. 비행 거리를 사거리와 따로 (물러나면 더 날아야 맞음). 피해는 **발당** |

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 공격 = **추상 SO** (구역 조건·스킬 효과와 같은 틀) | 기획이 유형을 하나 더 들고 올 때마다 코드가 늘지 않게 | |
| 맥락은 **`readonly struct MonsterAttackContext`**로 넘김 | 공격 에셋은 여러 몬스터가 공유하므로 "누구를 때리는지"를 자기 안에 들면 안 된다 | |
| 거리는 **평면 거리** | 높이 차이를 섞으면 지형에 따라 사거리가 달라진다 | |
| **최소 사거리** | 없으면 원거리 몬스터가 코앞까지 붙어서 쏜다 | |
| **예고 기본값 0** | 기획에 공격 예고가 있는지 미확인 (질문 2). 값만 넣으면 타이밍이 생김 | 지금 예고 연출은 없다 |
| 막혔을 때 멈춤 = 별도 값, **0이면 빈틈과 같게** | 막아낸 보람이 빈틈보다 짧으면 방패를 들 이유가 없다 | |
| 방어불가는 **공격 에셋의 `Kind`** | 판정 쪽 이음새(`PlayerHealth`)는 이미 있었다 | |
| 투사체는 **Rigidbody 없이 직접 이동 + `SphereCast`** | 투사체가 몬스터·광물을 밀면 배치가 흐트러지고 넉백과 힘이 섞인다. 한 프레임 구간을 통째로 훑어 빠른 탄이 얇은 벽을 지나치지 않음 | |
| 투사체는 **몬스터를 안 맞힘** | 자기 탄에 죽는 몬스터는 버그로만 보인다 | 첫 SphereCast 결과만 보므로 몬스터를 맞으면 그 프레임은 그냥 통과 |
| 피해 출처로 **탄 자신**을 넘김 | 쏜 몬스터를 넘기면 방패 각도를 몬스터 위치로 재서, 탄이 옆·뒤에서 와도 몬스터가 정면이면 막힌다. 기획 "뒤에서 맞으면 피해" | 대신 막혀도 쏜 몬스터는 경직되지 않는다 ([5-8](#5-8-몬스터-두뇌--monsterai)) |
| 프리팹에 `Projectile`이 없으면 **경고 후 반납** | 조용히 넘기면 "왜 안 맞지"를 한참 찾는다 | |

### 5-10. 몬스터 생성과 저장 — `MonsterSpawner` · `MonsterDeaths`

| 결정 | 왜 | 대가 · 주의 |
|---|---|---|
| 스포너는 **배치(Placed) / 랜덤(Random) 둘 다** | 기획서는 "지정 위치", 구두로는 랜덤. 어느 쪽이든 설정만 바꾸게 | |
| 랜덤은 **디자이너가 그은 영역 안에서 빈 칸 고르기** | 무엇이 나오는지는 에셋이 정하고 고르는 건 자리뿐 → 절차적 생성 금지와 안 부딪힘 | |
| 고른 자리는 **기억** (`Reroll`로만 다시 뽑음) | 기획: 구역 전투 초기화 시 "원래 배치로 다시 나온다" | |
| **구역당 스포너 하나**, 여러 종류를 `Group` 목록으로 | 구역 점령이 "이 구역 몬스터 전부"를 한 덩어리로 켜고 끄고 세야 한다 | |
| 빈 칸 판정 = **그리드 + 물리** (생물, 벽) | 그리드만 묻다가 ① 구역 벽(그리드 미등록) 속에 생겼고 ② 플레이어는 그리드에 없다 | |
| **자기 구역 안에만** 세움 | 남의 구역에 세우면 아무도 안 쫓는 허수아비가 되는데, 겉으로는 AI 고장처럼 보인다 | |
| 생성은 **비활성 → `Configure` → 칸 심기 → 켜기** | `Awake`가 정의에서 체력을 읽으므로. 칸은 죽음 기록이 몬스터를 알아보는 키 | |
| 치울 때 **`DestroyImmediate`** | 같은 프레임에 다시 세울 수 있다 (`PlacedBlocks`에서 당함) | |
| ⚠️ **런타임에 부르는 코드가 없다** | 씬에 스포너 3개가 설정돼 있지만 `Spawn()`을 부르는 곳이 없다. 지금 씬의 몬스터는 직접 배치된 프리팹 | 쓰기 시작하면 "시작 시 한 번 모으는" 구독자들(보상·팝업·체력바)이 새 몬스터를 모른다 |
| 죽음 저장은 **한 곳(`MonsterDeaths`)이 모아 한 항목** | 몬스터마다 `ISaveable`이면 저장 항목이 마릿수만큼 생기고 이름 짓기가 문제 | |
| 몬스터 식별 = **`GridPlacement` 칸 좌표** | 프리팹에 이미 있고 칸은 겹치지 않는다. 디자이너가 몬스터를 옮기면 그 기록만 어긋나는데, 맵을 고친 것이니 자연스럽다 | |
| **"죽었다"만 저장** (체력·위치 X) | 부활이 없다는 것이 확정 | 불러올 때 살아 있어야 할 죽은 몬스터는 `Respawn` |
| 부활 "없음"을 **재생성 시간 99999초**로 표현 | 몬스터 정의 에셋 13개 전부 | 코드상 "0 = 부활 없음"이지만 에셋은 99999. 사실상 같지만 27시간 뒤엔 살아난다 |

### 5-11. World에서 반복되는 패턴 · 걸린 것

**패턴**

| 패턴 | 어디서 |
|---|---|
| **존재 끄기** (GameObject는 살림) | 광물, 몬스터, 구역 벽 |
| **보상·연출은 이벤트로 넘김** | `Harvested`, `Died`, `Damaged`, `Picked` |
| **스테이션은 화면을 모름** (`OpenRequested`) | 제작대, 보관함 (+ Economy의 상점·변환기) |
| **생성 경로는 하나** | `PlacedBlocks.Place`, `DropService.Spawn` |
| **씬이 진실** (저장 시 목록 대신 씬 훑기) | `PlacedBlocks`, `MonsterDeaths` |
| **불러오기 전용 조용한 경로** | `MarkDeadSilently`, 드랍 전부 치우기, `DestroyImmediate` |
| **겹치면 미루고, 순서에 기대지 않음** | 광물 부활, 플레이어 불러오기 위치 ([3-5](#3-5-방패와-체력)) |
| **위치를 쥐는 곳은 하나** | 넉백 > 돌진 > 일반 이동, 공격은 이동을 부탁만 |
| **빠진 부품은 채우고, 잘못된 배선은 크게 알림** | `EnsurePickupCollider`, `LogError`/`LogWarning` |

**코드와 안 맞는 주석 · 확인할 것**

- `ItemDrop` 머리말 "시간이 지나도 사라지지 않는다" → 지금은 30초 수명이 있다 (`DropService`).
- `MonsterAI` 머리말의 상태 순서 설명(돌진 → 경직/넉백 → 빈틈 → 예고 → 리쉬 …)은 맞지만, "슬라임"을 예로 든 주석이 여럿 남아 있다. 지금 몬스터는 돌무더기 · 투척꾼 · 돌격꾼 · 골렘.
- `MonsterSpawner`가 런타임에 안 불린다 — 의도(에디터에서만 쓸 예정)인지, 구역 전투 초기화 연결이 빠진 것인지 확인 필요.
- 부활 없음을 99999초로 흉내 내는 대신 정의에 "부활 안 함" 스위치를 두거나 0으로 바꾸는 게 의도에 맞다.
