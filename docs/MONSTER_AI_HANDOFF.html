몬스터 상태머신 인계

몬스터 AI를 재설계할 사람이 읽는 문서예요. 지금 코드가 어떻게 움직이는지, 무엇을 지켜야 하는지, 어디가 아쉬운지, 어떤 순서로 익히면 좋은지를 담았어요. 재설계 방향은 후보와 장단점만 정리했고, 결정은 받는 분이 합니다.

1한 장 요약

상태는 "계산"된다

MonsterAI.FixedUpdate()가 매 물리 프레임마다 위에서부터 조건을 묻고, 처음 걸리는 곳에서 행동한 뒤 return해요. Current는 그 결과를 적어 두는 이름표일 뿐, 다음 행동을 정하지 않아요.

순서가 곧 규칙

돌진 → 경직 → 넉백 → 빈틈 → 예고 → 끈(leash) → 탐지·구역 → 후퇴 → 공격 → 추적. 위에 있는 것이 먼저 가로채요.

공격은 에셋이 정한다

AI는 "무엇을 칠지"를 모르고, MonsterDefinition의 공격 목록에서 지금 쓸 수 있는 첫 번째를 고를 뿐이에요. 공격 종류가 늘어도 AI 파일은 안 늘어나요.

위치는 한 명만 쥔다

넉백 중엔 Knockback, 돌진 중엔 MonsterAI가 몸을 옮겨요. 공격 에셋은 몸을 직접 옮기지 않고 AI에 부탁해요.

먼저 알아둘 것: 기존 문서와 코드가 어긋난 곳 docs/CODING_GUIDE.md 2장의 "한 프레임 순서"는 돌진·후퇴가 생기기 전 버전이에요. 경직과 빈틈을 한 줄로 묶어 적었고, 돌진(Lunge)과 후퇴(Retreat)가 빠져 있어요. 이 문서의 4장이 지금 코드(MonsterAI.cs:158-268) 기준이에요.

재설계 전에 읽을 순서

  1. 이 문서 4장(다이어그램)과 8장(지켜야 할 규칙)
  2. MonsterAI.cs의 FixedUpdate 한 함수 (110줄)
  3. 이 문서 9장(한계)과 10장(후보)
  4. 코딩이 처음이라면 11장의 연습 과제를 1번부터 차례로

함께 보면 좋은 문서: docs/CODING_GUIDE.md(몬스터 코딩 규칙), docs/CONTENT_HANDOFF.md(에셋만으로 하는 작업), docs/DECISIONS.md(확정된 수치와 이유), docs/TODO.md의 21·22·28번(상태머신에 영향이 큰 남은 일).

8재설계해도 지켜야 할 규칙

코드 주석과 기획에서 모은 것들이에요. 구조를 통째로 바꿔도 아래가 그대로 성립해야 해요. 각 줄의 "확인 방법"을 플레이 모드 회귀 체크리스트로 쓰세요.

#규칙왜확인 방법
1위치는 한 곳만 쥔다. 넉백 중 AI는 이동하지 않고, 공격 에셋은 몸을 직접 옮기지 않는다둘이 같이 MovePosition하면 밀림이 상쇄돼 넉백이 안 보인다몬스터를 때려서 뒤로 밀리는지
2피격 시 경직 0.22초, 예고·돌진 취소. 경직은 넉백(0.16초)보다 길다밀리는 동안 쌓인 예고가 끝나자마자 터지면 안 된다 (DECISIONS.md)돌무더기 예고 중에 때리면 공격이 안 나오는지
3죽는 타격도 예고를 끊는다Damaged가 사망보다 먼저 나가는 이유예고 중에 막타 → 공격이 안 나오는지
4예고 중에는 제자리, 표적만 바라본다쫓아가며 때리면 예고가 피할 시간이 못 된다예고 중 옆으로 걸어 피해지는지
5근접은 내지르는 순간 사거리를 다시 본다피했는데 맞으면 예고가 신호가 아니다4번과 같이
6쿨다운은 공격마다 따로, 내지른 순간부터 센다하나로 묶으면 근접 뒤 원거리도 잠긴다 / 예고부터 세면 예고 긴 공격이 더 자주 나간다골렘: 내려치기 쿨 중에도 접촉 피해가 들어오는지
7빈틈(Recovery)과 쿨다운은 다른 축. 빈틈 중엔 이동·다른 공격 모두 없음빈틈이 플레이어의 반격 창돌무더기 휘두른 직후 0.8초간 접촉 피해가 없는지
8방패에 막히면 StaggerWhenBlocked(0이면 Recovery)만큼 멈춘다막아낸 보람이 빈틈보다 짧으면 방패를 들 이유가 없다방패로 막은 뒤 몬스터가 멈추는지
9공격 우선순위 = 에셋 목록 순서. 코드에 적지 않는다디자이너가 순서로 정한다목록 순서를 바꾸면 행동이 바뀌는지
10사거리 안인데 쓸 공격이 없으면 더 다가가지 않는다원거리형이 코앞까지 붙는다투척꾼이 쏜 뒤 다가오지 않는지
11다른 구역의 플레이어는 표적이 아니다. 구획 밖 몬스터는 이 규칙을 안 쓴다차단벽 너머 어그로 버그(3차 피드백 1번). 구역이 없는데 요구하면 아무도 안 쫓는다경계벽 너머에서 서 있을 때 안 쫓아오는지
12후퇴로 자기 구역을 벗어나지 않는다기획 "구역 밖으로 이동하지 않는다"투척꾼을 벽 쪽으로 몰기
13돌진은 예고 끝 순간의 방향으로 고정, 한 번만 맞히고, 벽에서 멈춘다기획 "중간에 방향을 바꾸지 않는다"예고 중 옆으로 피하면 빗나가는지
14HomeRegion은 Start에서 한 번에 잡지 않는다같은 오브젝트 안 Start 순서 미보장 → 원점 구역을 봄구역 안 몬스터가 정상적으로 쫓아오는지
15이동은 FixedUpdate + Rigidbody.MovePosition + Time.fixedDeltaTime콜라이더 관통, 프레임레이트 의존 방지구조물을 뚫고 지나가지 않는지
16예고 시작 시 Telegraphing, 돌진 시작 시 Lunged 이벤트를 유지한다연출이 들을 자리. AI가 연출을 직접 부르지 않는다이벤트에 임시 로그를 달아 확인

그리고 CODING_GUIDE.md 7장 체크리스트와 Tools ▸ ForagerCP ▸ 씬 검사(오류 0 / 경고 0)도 그대로 적용돼요.

9지금 구조의 한계와 확인된 문제

코드를 읽어서 찾은 것들이에요. 확인은 코드상 확실한 것, 추정은 플레이로 확인이 필요한 것, 구조는 버그는 아니지만 확장을 어렵게 하는 것이에요.

구조적 한계

구조 상태가 "결과"이지 "원인"이 아니다

진짜 상태는 6장의 값 7종에 흩어져 있고, Current는 매 프레임 계산 결과를 적는 이름표예요. 그래서 "상태에 들어갈 때 한 번", "나갈 때 한 번" 같은 일을 넣을 자리가 없어요. 예고 시작 이벤트가 Begin 안에 있는 것도 그 때문이에요. 연출·사운드·애니메이션이 붙기 시작하면 "언제 상태가 바뀌었나"를 알아야 하는데, 지금은 바뀌었다는 신호(StateChanged)가 없어요.

구조 우선순위가 한 함수의 if 순서에 묶여 있다

새 상태(예: 보스의 패턴 전환, 도망, 무리 행동)를 넣으려면 110줄짜리 FixedUpdate에서 끼워 넣을 자리를 찾아야 하고, 위치를 잘못 잡으면 다른 상태를 몰래 가로채요. 파일 머리 주석이 "건드릴 때 이 순서를 먼저 확인할 것"이라고 경고하는 이유예요.

구조 몬스터 종류별 행동 차이를 넣을 곳이 없다

지금은 모든 몬스터가 같은 판단 순서를 쓰고, 차이는 공격 에셋과 수치에서만 나와요. 보스처럼 "체력 50% 아래면 다른 패턴"이 필요해지면 AI 쪽에도 종류별로 갈라지는 지점이 필요해요.

이름표(Current)가 틀리는 곳

확인 경직·넉백·낙하 구제 중 Current가 직전 상태로 남는다

MonsterAI.cs:168-187의 세 분기는 Current를 바꾸지 않고 return해요. 추적 중에 맞으면 경직 0.22초 동안 Current == Chase로 보여요. CODING_GUIDE.md 9장은 "몬스터가 가만히 있으면 Current를 찍어 보라"고 하는데, 바로 이 경우에 틀린 답을 줘요. 지금 Current를 읽는 코드는 없어서 게임 동작에는 영향이 없어요.

구조 Attack이 두 뜻으로 쓰인다

"지금 공격을 시작함"과 "사거리 안에서 쿨다운을 기다림"이 같은 이름이에요 :250, :260. 애니메이션을 붙이면 기다리는 동안에도 공격 모션이 나가요.

동작 문제

추정 끈(leash) 경계에서 Return ↔ Chase가 번갈아 바뀐다

Return은 "집에 도착할 때까지"가 아니라 "이번 프레임에 끈 거리를 넘었으면"이에요 :219. 플레이어가 끈 경계 근처에 있으면, 한 걸음 돌아가 경계 안으로 들어온 순간 다시 추적 → 다시 밖 → 다시 복귀가 반복돼 경계에서 떨 수 있어요. 지금은 구역 판정이 먼저 표적을 끊어 주는 경우가 많아 덜 보이지만, 넓은 구역에서는 나타날 수 있어요. "복귀를 시작하면 집에 닿거나 일정 시간이 지날 때까지 유지"처럼 상태가 자기 자신을 붙잡는 기능이 필요한 대표 사례예요.

확인 돌진 뒤 빈틈이 돌진 시간만큼 짧아진다

Fire가 빈틈 끝 시각을 "지금 + Recovery"로 적은 직후 돌진이 시작되고, 돌진 중에도 그 시계가 흘러요 :323, :176. 돌진수는 거리 5 ÷ 속도 11 ≈ 0.45초를 달리므로, 멈춘 뒤 실제 빈틈은 1.2초가 아니라 약 0.75초예요. 돌진이 Recovery보다 길면 빈틈이 아예 없어요. TickLunge 주석("멈춘 뒤의 빈틈은 Fire가 이미 걸어두었다")은 멈춘 뒤부터 센다고 읽혀서 의도와 다를 가능성이 커요. 기획 확인이 필요해요.

확인 구석에 몰린 투척꾼이 아무것도 안 한다

플레이어가 4m 안으로 붙었는데 뒤가 구역 경계면 TryRetreat가 실패해요. 이어서 PickAttack은 최소 사거리 때문에 투사체를 못 고르고, MaxAttackRange(8) 안이라 "제자리 대기"로 빠져요 :240-263. 결과적으로 맞기만 하는 허수아비가 돼요. 기획 의도(구석에 몰면 쉬워진다)인지, 옆으로 빠지거나 근접 공격을 줘야 하는지 확인이 필요해요.

구조 근접과 원거리를 같이 가진 몬스터는 붙으면 근접을 못 쓴다

후퇴 판단이 공격 고르기보다 먼저라서, 최소 사거리가 있는 공격이 하나라도 있으면 그 거리 안에서는 항상 물러나려 해요. 지금은 이런 조합의 몬스터가 없지만, 보스를 만들 때 걸려요.

추정 투사체를 방패로 막아도 투척꾼은 멈추지 않는다

OnBlocked는 막힌 공격의 source가 자기 자식인지로 "내 공격인가"를 판단해요 :126. 그런데 투사체는 탄 자신을 source로 넘기고(방패 각도를 탄 기준으로 재기 위해), 풀에서 꺼낸 탄은 몬스터의 자식이 아니에요. 그래서 투사체를 막으면 막힘 경직이 걸리지 않아요. 원거리 공격은 멈출 필요가 없다는 의도일 수도 있지만, 주석이나 기획 문서에 그런 말은 없어요.

구조 경직으로 무한히 묶을 수 있다

피격은 예고를 취소하지만 쿨다운은 소모하지 않아서, 경직이 풀리면 곧바로 같은 공격의 예고를 다시 시작해요. 플레이어가 0.22초보다 빨리 때리면 몬스터는 영원히 못 때려요. "넉백을 hitstun으로 승격"이 확정 스펙이라 의도된 동작이지만, 보스에서는 슈퍼아머 같은 예외가 필요해질 거예요.

주변 코드의 어긋남 (재설계 범위 밖, 참고)

  • 정리 필요 재등장: MonsterDeaths 주석은 "리스폰 없음 확정"이라는데, 구역 몬스터 에셋은 RespawnDelay = 99999(약 28시간 뒤 재등장)이고 슬라임은 0(재등장 없음)이에요. "없음"을 뜻하는 값이 두 가지예요.
  • 참고 MonsterSpawner.Respawn()은 지우고 새로 만들어요(DestroyImmediate). CODING_GUIDE.md 6장은 전투 초기화를 "죽은 것도 살려서 제자리에 돌려놓기"로 하자고 적었어요. TODO 22번(전투 초기화)을 할 때 AI 타이머 초기화 함수가 필요해요. 지금은 Respawn해도 AI의 쿨다운·빈틈 값이 그대로 남아요.
  • 참고 플레이어를 두 번 찾아요: Awake에서 _player, Start에서 _target. 둘은 같은 오브젝트예요.
  • 참고 회전은 transform.rotation을 직접 써요. 이동 규칙(MovePosition)과 달라요. 지금 문제는 없어요.

10재설계 방향 후보

결정은 받는 분 몫이에요. 판단 재료로 장단점을 정리했어요. 어느 쪽이든 8장 규칙과 "공격은 에셋" 구조는 유지하는 걸 전제로 했어요.

A. enum + switch, 들어가기/나가기 추가

지금 파일 안에서 ChangeState(next) 하나로만 상태를 바꾸고, 바뀔 때 Exit(old)/Enter(new)를 부르게 해요. FixedUpdate는 switch (Current)로 상태마다 나뉘어요.

장점 바꾸는 양이 적고, 파일 하나 안에서 끝나요. 첫 재설계로 익히기 좋아요.
단점 상태가 늘면 switch가 길어지고, 몬스터 종류별 차이를 넣기 어려워요.

B. 상태 클래스 (State 패턴)

상태마다 Enter / Tick / Exit를 가진 클래스를 만들고, AI는 "지금 상태 객체"에 일을 맡겨요. 전이는 각 상태가 "다음은 누구"를 돌려줘요.

장점 상태 하나를 고칠 때 파일 하나만 봐요. 보스 전용 상태를 따로 추가하기 쉬워요.
단점 파일이 많아지고, 상태끼리 공유하는 값(타이머, 표적)을 어디에 둘지 설계가 필요해요.

C. 전이 표를 데이터(에셋)로

B 위에 "어떤 조건에서 어느 상태로"를 ScriptableObject 목록으로 두어 디자이너가 조합해요. 공격을 에셋으로 만든 지금 방침과 같은 방향이에요.

장점 몬스터 종류별 행동 차이를 코드 없이 만들어요.

Behavior Tree 패키지나 Animator 상태머신(StateMachineBehaviour)을 써요.

장점 그래프 편집기가 생겨요.
단점 새 도구를 배우는 비용, 패키지 의존. 지금 코드의 "시각 비교" 방식과 섞을 때 다시 소유권 문제가 생기기 쉬워요.

어떤 방향이든 먼저 정할 질문

  1. 경직·넉백을 상태로 볼까, 상태 위에 겹치는 "방해"로 볼까? 지금은 후자에 가까워요(이름 없이 가로챔). 상태로 만들면 이름표 문제가 풀리고, 겹침으로 두면 "빈틈 중 맞음" 같은 조합이 단순해요.
  2. "계속 다시 계산"과 "한번 들어가면 유지" 중 어느 쪽이 기본인가? Return 진동은 유지가 필요하다는 신호이고, 지금의 즉각 반응(사거리 들어오면 바로 공격)은 다시 계산의 장점이에요.
  3. 시간은 어디서 읽나? TODO 28번(창 열면 정지)을 생각하면 Time.time을 직접 부르지 말고 한 곳을 거치게 해 두는 게 나아요.
  4. 전투 초기화(TODO 22번)에서 AI를 어떻게 처음 상태로 되돌리나? ResetBrain() 같은 진입점이 있어야 해요.
  5. 무엇을 밖으로 알리나? 최소한 StateChanged(old, new) 하나는 있어야 연출·사운드·디버그 표시가 붙어요.
안전하게 바꾸는 순서 제안 ① 지금 동작을 8장 체크리스트로 한 번 녹화하거나 기록 → ② 동작은 그대로 두고 구조만 바꾸기(이름표 문제만 같이 고침) → ③ 체크리스트 재확인 → ④ 그다음에 9장 동작 문제를 하나씩, 기획 확인 받고 고치기. 구조 변경과 동작 변경을 한 커밋에 섞지 않으면 무엇이 깨뜨렸는지 바로 찾을 수 있어요.
